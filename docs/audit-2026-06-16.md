# Aira AI — Codebase Audit (2026-06-16)

Source: graphify graph (commit `aed7c6df`) + direct source read at HEAD `aafff7d`.
Scope: logical errors + gaps blocking a top-tier, horizontally-shippable SaaS.

---

## 1. Architecture reality check (the linchpin)

The whole backend assumes **one process**. Start command is `uvicorn app.main:app` with
no `--workers`, and `lifespan` starts the in-process `AsyncIOScheduler` **unconditionally**
(no leader election / worker-0 gate). `supabase-py` is a **synchronous/blocking** client, so
within a single event loop each handler runs read→write to completion without yielding — many
"races" below are therefore *latent*, not live today.

The moment you scale (Render `numInstances > 1`, or add `--workers N`), this breaks:
- **Every APScheduler job fires N× in parallel** (broadcasts, retries, sweep, callback-reassign,
  re-engagement, decay, token-health) — one scheduler per process, no distributed lock.
- The assignment read-then-write stops being atomic across processes.

This single assumption is the #1 blocker to "horizontally shippable." Fix path: move scheduled
work to a dedicated worker (separate Render service) or gate the scheduler to one process, and/or
move jobs to pg_cron + a claimable queue table. Until then, the product is single-instance-only.

## 2. Logical errors / correctness bugs

### CRITICAL
- **Service-role key bypasses RLS app-wide.** `db/supabase.py` builds one global client with
  `supabase_service_key`. RLS is "enabled on all tables" (tech debt note) but provides **zero**
  protection for app queries — tenant isolation rests 100% on every query remembering
  `.eq("tenant_id", ...)` (Invariant 6). One forgotten filter = cross-tenant leak. A line-based
  scan of `routes/` shows ~many `.table(...)` chains; most carry the tenant filter on a
  continuation line, but the surface is large enough that a real audit is mandatory.
  → Run the `tenant-auditor` agent; longer term, use a per-request authed client (anon key + user
  JWT) so RLS is actually enforced as defense-in-depth.

### HIGH
- **`auto_assign_lead` clobbers existing assignments.** [assignment.py:177](backend/app/services/assignment.py#L177)
  does `update({"assigned_to": chosen}).eq("id", lead_id)` with **no `.is_("assigned_to","null")`
  guard**. The safety check at L131 is read-then-write (TOCTOU). Sequentially this causes
  reassignment churn (sweep + inbound `maybe_assign_lead` racing on the same lead); under
  multi-process it double-assigns. Fix: conditional update guarded on null + check `res.data` to
  confirm the claim won. Also the least-loaded loop runs **one count query per caller** (N+1) on
  every assignment, including the 200-lead sweep — a perf cliff.
- **Synchronous Groq calls in the WhatsApp webhook before returning 200.** `generate_reply` is
  correctly backgrounded ([webhook.py:450](backend/app/routes/webhook.py#L450)), but
  `route_booking_intent` (L417), `compute_score` (L420) and `compact_conversation` at
  msg_count≥10 (L440) are **awaited inline** — and all three hit `await client.chat.completions.create`.
  That's up to 3 sequential LLM round-trips inside Meta's webhook deadline → timeouts → Meta
  retries (duplicate processing) and eventual webhook disablement. Move them to `background_tasks`.
- **Broadcast can strand in `running` on process death.** `execute_broadcast` CASes
  `pending→running` ([broadcast_executor.py:54](backend/app/services/broadcast_executor.py#L54))
  and the `except` correctly flips to `failed`, but a **hard kill** (Render redeploy, OOM, SIGKILL)
  mid-loop leaves the row `running` forever: half-sent, never retried, never surfaced. No
  stale-`running` reaper (flow-runs have one; broadcasts don't).

### MEDIUM
- **`confirm_booking` is idempotent but not atomic.** [booking_flow.py:513](backend/app/services/booking_flow.py#L513)
  reads `status` then updates — two concurrent Razorpay webhook retries can both pass the
  `!= "confirmed"` check and double-send the WhatsApp confirmation. Use a guarded update
  (`.eq("status","pending")`) and act only if `res.data`.
- **Re-engagement dedup is app-level, not a claim.** `process_due_reengagements` has "already
  processed" checks but no CAS; safe single-instance, double-sends under multi-instance.

## 3. Security gaps

- **`/sentry-debug` (1/0) is live and unauthenticated** ([main.py:586](backend/app/main.py#L586)).
  Remove from production.
- **CORS allows any `*.vercel.app` with `allow_credentials=True`** ([main.py:519](backend/app/main.py#L519)).
  Any Vercel-hosted origin can make credentialed requests. Pin to known prod origins.
- **No rate limiting** on the authed API or the public webhooks (webhooks are signature-gated,
  which helps, but the API has none). Security checklist item.
- **Sentry `traces_sample_rate=1.0`** — 100% tracing is a cost/perf liability at volume; sample.

## 4. Pervasive theme: silently swallowed failures

Many `except Exception: pass` / `except: pass` blocks hide real failures — e.g. webhook
opt-out + message-insert paths, broadcast message/no-reply-count inserts
([broadcast_executor.py:226](backend/app/services/broadcast_executor.py#L226),
[#L230](backend/app/services/broadcast_executor.py#L230)). For a "top-tier" product these need at
least a `logger.warning`; today a failed message-log or counter is invisible.

## 5. Product / brand correctness

- **Temple-vertical copy still hardcoded** despite the generic-B2B-SaaS North Star and the
  migration-082 de-hardcoding. The Razorpay confirmation message hardcodes "Namaskaram",
  "Devotee", 🙏 ([bookings.py:88](backend/app/routes/bookings.py#L88)) and the `bookings` table
  carries a `devotee_name` column. Any non-temple tenant gets wrong messaging. Move copy to
  per-tenant settings; rename the column generically.

## 6. Gaps to reach "top-tier shippable"

| Area | Gap | Fix |
|---|---|---|
| Scaling | Single-process assumption (§1) | Worker service or pg_cron + queue; gate scheduler |
| Durability | Async work on FastAPI BackgroundTasks + in-proc scheduler — lost on restart | Durable job queue (claimable table / pg-boss-style) |
| Observability | health check verifies **1 of 7** scheduler jobs; no dead-job alerting; no request correlation IDs | Per-job heartbeats + alert; structured logging |
| Idempotency | Outbound sends rely on CAS only; no idempotency keys | Dedup key per (broadcast,lead) send |
| Tenancy | RLS bypassed by service key (§2) | Authed per-request client |
| Rate limiting | none (§3) | slowapi / gateway limits |
| Tests | concurrency paths (assignment race, broadcast CAS, webhook dedup) untested; project mandates 80% | add targeted tests |

---

## Suggested priority order
1. Move the 3 inline-Groq calls in the webhook to background (active prod risk: Meta timeouts).
2. Guard `auto_assign_lead` + `confirm_booking` with conditional updates (single-process bugs today).
3. Remove `/sentry-debug`; pin CORS.
4. Run `tenant-auditor` over all routes.
5. Decide the scaling model (worker service vs pg_cron) before enabling >1 instance.
6. De-hardcode temple copy; add broadcast stale-`running` reaper; replace `except: pass` with logs.
