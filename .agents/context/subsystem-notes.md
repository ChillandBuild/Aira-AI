## Domain: `www.bloommatrix.in/aira` (Next.js basePath, 2026-07-02)
- Aira is proxied under Bloom Matrix's domain via Vercel rewrite (`/aira` + `/aira/:path*` → Aira's Vercel URL) + Aira's own `next.config.mjs` `basePath: "/aira"`. Two separate Vercel projects, not merged.
- **basePath does NOT auto-prefix**: `public/` folder assets (`sw.js`, icons, favicon — must hardcode `/aira/...` in every reference, including inside `public/sw.js` itself since it's a static file Next never touches), `metadata.icons`/`metadata.manifest` string fields in `layout.tsx`, `app/manifest.webmanifest/route.ts` fields (`start_url`/`scope`/`id`/icon `src`), and any raw `<a href="/...">` — **including dynamic `href={someVar}`, not just literal strings**. It DOES auto-prefix `next/link`, `useRouter().push()`, `redirect()` (server actions/middleware — `NextResponse.redirect(nextUrl.clone())` in middleware also auto-reapplies basePath), and `next/image`.
- **Audit trap**: a literal-string grep (`grep -rn 'href="/[^/"]'`) will NOT catch `href={item.href}` (array/variable-driven nav, e.g. `operator-sidebar.tsx`'s top nav) — this exact gap caused a real prod 404 on Fleet/Schedulers/Audit Log after the migration. Full sweep needs `grep -rn '<a\b'` and manual triage, not a literal-string pattern. Also: `grep -E` does not support `(?!...)` lookahead — a pattern using it silently matches nothing rather than erroring, which reads as a false "all clear."
- Backend CORS (`backend/app/main.py`) must explicitly list the new origin(s) — it does not infer them from `FRONTEND_URL`-adjacent domains or wildcard beyond `*.vercel.app`. `https://www.bloommatrix.in` and `https://bloommatrix.in` are both now in the allowlist.
- **`basePath` applies to plain local `npm run dev` too, not just the production Vercel rewrite** — there is no proxy locally, so every URL still needs the literal prefix: `http://localhost:3000/aira/operator/login`, not `http://localhost:3000/operator/login` (the latter 404s). Easy to forget when testing locally since the rewrite that makes it invisible in production doesn't exist on `localhost`.

## Broadcast delivery & retry
- **Delivery truth = `messages.delivery_status`** (+ `delivery_error_code`/`_title`), set by the delivery webhook (webhook.py ~L463-517). `broadcast_recipients.send_status` only reflects **Meta API acceptance** (returns message_id), NOT delivery — it's the WRONG signal for "did the lead receive it."
- **`broadcast_recipients.send_status` delivery-failed flip is DEAD CODE** (3 reasons: CHECK constraint rejects `'delivery_failed'`; executor stores `meta_message_id` only on `messages`, not the recipient row, so `.eq` matches nothing; errors swallowed). Never trust `send_status` for delivery.
- **Per-send / per-broadcast attribution = `services/delivery_status.py` `nearest_record`/`nearest_status`** (the outbound `messages` row nearest in time, −2min/+10min). Used by all 3 sites (upload.py history+segment CSV, tags.py stats) so they never disagree. **NEVER** use max-priority-in-window (an adjacent broadcast's `sent` masks this one's `failed`) or any-failed-in-window (over-attributes).
- **`leads.whatsapp_undeliverable`** = sticky lead-level "is this number currently reachable" flag (resets on inbound + delivered/read receipt). Good for re-engagement skip; **WRONG for per-broadcast stats** (never reset per send).
- **Error codes:** `131049` = marketing cap ("healthy ecosystem engagement") — manifests async as a `failed` webhook OR a silent accepted-never-delivered; retry-worthy. `131026` = wrong number → set `whatsapp_undeliverable`, never retry. Transient set `{131049,131048,131056,130472}` does NOT set undeliverable.
- **Auto-retry removed (migration 170, 2026-08-11).** The feature described in migration 104 (per-broadcast retry toggle, `services/broadcast_retry.py`, retry timeline UI, `retry_enabled`/`retry_time`/`retry_max_attempts`/`retry_of`/`retry_attempt`/`retry_completed_at` on `scheduled_broadcasts`) is gone end-to-end — service deleted, routes/scheduler job removed, columns dropped live. `broadcast_recipients.extra_cols` (same migration 104) was kept — it's used on every send for template personalization, unrelated to retry despite sharing a migration. See `.agents/decisions/log.md`.
- Both `broadcast_recipients.meta_message_id` and `leads.whatsapp_undeliverable` exist in prod but were added manually — **no migration**. Durable fix (not done): store `meta_message_id` on the recipient at send time for an exact join.

## Scoring (`services/scoring_engine.py` v2, on main)
- Composite: `arc + intent_delta + engagement`, clamped 1–10. Rejection sentinel → instant score=1/segment=D, bypasses segment lock entirely. Segment lock (non-rejection): upgrade immediate, drop needs 2 consecutive confirmations.
- **`_REJECTION_PATTERNS` covers EN + Tamil + Tanglish + Hindi + Hinglish + Telugu + Kannada + Malayalam (2026-07-29).** EN list is phrase-shaped, not just "stop"/"not interested" — also message/msg/text/call variants ("don't message me", "stop calling"), "not needed"/"not required"/"no interest"/"leave me alone"/"remove my number". Tanglish "don't message/call" is a shape regex (`panna{1,2}(dh|th)(ee|e|i)nga`) because romanized spelling varies wildly in real chat (`pannadhinga` vs `pannadheenga` vs `pannathinga` all seen live) — if a real message with clear reject intent still lands as Hot/Warm instead of D, suspect an uncovered spelling variant here before anything else. Telugu/Kannada/Malayalam only have the 3 core native-script words each (not needed/stop/don't want) — **not native-speaker verified**, treat as best-effort until someone who speaks them reviews. Deliberately did NOT add bare "no need" (EN) — too generic, collides with benign hedges like "no need to worry".
- **Arc-scoring LLM is Gemini `gemini-3.1-flash-lite` as of 2026-07-29 (was Groq Llama 3.3 70B, commit `22979bc`).** Llama 3.3's officially supported languages don't include Tamil; live-verified the same byte-identical Tanglish opening message scoring 6/7/8 across three leads on Groq. Matches the 2026-07-18 `analyze_call` migration below — `conversation_compactor.py` also moved the same day, see decisions/log.md 2026-07-29. Fallback on failure = current arc, not hardcoded 5.
- **`_score_arc()`'s Gemini call silently failed on every invocation from the Groq→Gemini migration until fixed later the same day (2026-07-29)** — it carried over `max_tokens=4` from the old Groq code unchanged. Live-tested against the real endpoint with the actual production prompt: `gemini-3.1-flash-lite` returns an **empty string** at `max_tokens=4` every time; `max_tokens=6` and up return the real digit reliably. Every arc score computed in that window silently fell back to whatever score existed before — and the `arc_updated` flag / UI `⚡arc` badge fires regardless of whether the LLM call actually succeeded or silently fell back, so there was no way to tell the two apart from the UI. Fixed to `max_tokens=8`. **If arc ever looks frozen again despite fresh `⚡arc` badges, suspect a token-budget truncation before assuming the rubric is just reading the conversation as low-intent.**
- **Ad-prefilled CTWA messages are marked and down-weighted in the arc prompt.** `messages.via_ad_referral` (migration 150, 2026-07-29) is true when the inbound message arrived with Meta's `referral.source_type == "ad"` — i.e. it's the WhatsApp click-to-chat ad's own pre-filled CTA text, not something the lead composed. `_score_arc`'s conversation transcript prefixes those lines with `_AD_PREFILL_MARKER` (`[ad-prefilled entry message]`) and the prompt explicitly tells the LLM to score it as neutral first-contact (5-6), never as composed interest — otherwise Meta's own auto-fill wording (which can contain intent-sounding words like "detailed"/"urgent") would inflate the arc score. Leads from the same CTWA campaign send byte-identical opening text — don't mistake that for the lead's own words when investigating a scoring report.
- **Escalation/handover follow-up messages are similarly marked (2026-07-29).** A lead chasing an unresolved handover ("still no one contacted me", "when will they call") reads to the arc LLM as dismissive/frustrated and drags the score down even though the lead is still engaged — the frustration is about a stalled callback, not the product. Messages sent inside a `chat_handovers` open window (`opened_at` minus a 5-minute pre-buffer, since `opened_at` is stamped a few seconds after the triggering message — through `resolved_at` or now if still pending) get prefixed `_ESCALATION_MARKER` (`[handover follow-up]`) and the prompt is told not to let them lower the score. Live-tested head-to-head on a real stuck lead (marker present vs absent) — the marker applies correctly but didn't move the score in that specific case, so treat this as a plausible mitigation, not a proven fix, until it's observed changing a real outcome.
- **Score History was permanently empty for every lead until 2026-07-29 — silent `KeyError`, not a data problem.** `record_stage_event()`'s metadata build in `ai_reply.py` referenced a `"decay"` key that `compute_score()` stopped returning on 2026-07-26 (see that entry below); the resulting `KeyError` was swallowed by a broad `except Exception`, so `lead_stage_events` never got a `score_updated`/`segment_changed` row even though `leads.score`/`segment` updated correctly. Same bug also skipped `maybe_assign_lead()` (score-triggered auto-assignment) on every scored reply, main path only. Fixed by deleting the two dead `"decay"` references — if Score History is empty again in the future, suspect a *new* stale-key regression in that metadata dict before assuming it's a data/query issue.
- **No time-based decay (removed 2026-07-26, explicit user decision).** There used to be a bidirectional `decay` term (−4 stale over 30d+ ... +3 for replying within 1h) plus a 6-hourly `apply_engagement_decay_all` scheduler job that could silently move a lead's segment purely from the clock, with zero new message. Both are gone — `_compute_decay()`, the scheduler job, and `score_engagement_delta` writes are all deleted. A lead's score/segment now **only** changes when they send a new message; going silent has zero effect, in either direction. See decisions/log.md 2026-07-26.
- **The segment-A/assigned gate is GONE (2026-06-01).** Scoring fires on every inbound unconditionally.
- **Correction (2026-07-26): the "Per-broadcast scoring" claim below is stale — verify before relying on it.** `broadcast_lead_scores` (migration 076, `UNIQUE(broadcast_id, lead_id)`) is still real and still **seeded** score=5/seg=C at send time (`broadcast_executor.py`, `upload.py`). But `compute_score()` as it exists today takes **no `broadcast_context` parameter** and does not write to `broadcast_lead_scores` or `lead_tag_interest` at all — confirmed by reading the live function signature and grepping both files for writers. Whatever currently keeps a per-broadcast row's score in sync after a reply (if anything still does) was not traced this session — don't assume the old rollup-on-reply description is still accurate. Needs a fresh investigation; see active-backlog.md.
- `lead_scorer.py` (legacy two-pass) is still called only on the AI-disabled branch — tech debt to retire (see backlog).

## Lead visibility across Dashboard / Segments / Conversations (2026-07-25)
- **These three surfaces count three genuinely different populations of leads by design — don't assume they should ever show identical numbers per segment.** Dashboard's `/overview` `by_segment` = every non-deleted lead. Segments page (`/api/v1/leads/`) = same, minus `opted_out` and `whatsapp_undeliverable`. Conversations (Shared Inbox) = only leads with real message activity (RPC `get_conversation_leads` — an actual inbound, or a genuine non-template outbound) or pinned, minus archived/blocked.
- **The Shared Inbox now paginates ("Load more")** — `conversations/page.tsx`/`conversation-list.tsx`, offset-based against the existing `GET /api/v1/conversations?limit&offset` (backend already supported `offset`, frontend just never used it before 2026-07-25). Before this it was hard-capped at the 50 most-recent-active conversations with no way to see more, so eyeballing a segment's count from the inbox always undercounted — older/cold leads are the ones most likely to fall off a recency-sorted page. If a future count-mismatch report shows Conversations dramatically lower than Dashboard/Segments for a segment with real message history, check whether "Load more" was actually clicked before assuming a new bug.
- **`whatsapp_undeliverable` misclassification (see decisions/log.md 2026-07-25): only Meta error `131026` genuinely means the recipient's number is bad** (`webhook.py`'s `PERMANENT_UNDELIVERABLE_ERROR_CODES`). Never add another code to that set without confirming from Meta's docs (or a live-observed failure) that it's truly per-recipient, not account-level (e.g. `131031` "Business Account locked") or request-level — an account-wide restriction previously got misattributed to individual customers' phone numbers this way, silently hiding 56 healthy leads from one tenant's Segments/CSV/re-engagement.

## AI provider keys & billing model (all providers, 2026-07-17)
- **Every provider is strictly per-tenant, zero platform fallback** — Sarvam, Gemini, OpenAI, Groq, Jina. `require_tenant_setting(key, tenant_id)` raises if the tenant hasn't configured it; there is no silent drop to a platform/env-var key anywhere in the AI call paths. This is deliberate: **the operator (not the client) pastes each tenant's own keys into the operator console** so each provider's own dashboard shows accurate per-client cost/token usage — a platform fallback would silently defeat that and hide real cost exposure. Don't reintroduce an `x or settings.y_api_key`-shaped fallback in any new AI code path; it undoes the whole point.
- **`ai_reply_model` itself now has zero silent fallback too (2026-07-18)** — previously fell back to a hardcoded `_DEFAULT_REPLY_MODEL = "sarvam-30b"` constant when a tenant hadn't explicitly configured one. (The removal was originally justified by a "sarvam-30b is deprecated" claim that the operator later corrected as **wrong** — sarvam-30b is live. The decision stands on its own rationale anyway: Sarvam is one of four equal reply providers — Sarvam/Groq/Gemini/OpenAI — each selected per tenant by the operator, so no provider deserves a hardcoded default.) `_resolve_reply_model()` now calls `require_tenant_setting("ai_reply_model", tenant_id)`, same contract as every provider API key — an unconfigured tenant gets no AI replies at all (fails into the existing log-and-skip handler at `webhook.py`'s `generate_reply` call site). The operator console's model picker (`config.tsx`) also stopped labeling Sarvam 30B as "Default. Best fit..." — it's still selectable, presented as a peer of the other providers rather than the recommended choice. Don't reintroduce a `_DEFAULT_REPLY_MODEL`-shaped constant.
- **Only exception: `meta_app_secret`.** Stays platform-critical, but structurally, not as a billing choice — there's one shared Meta Developer App behind every tenant's WhatsApp Embedded Signup, so there's nothing to make per-tenant. (It IS still stored per-tenant in `app_settings` for `verify_meta_signature`'s uniform lookup, auto-copied from the platform value during Embedded Signup — that's a lookup-convenience detail, not a second Meta app per client.)
- **Jina bridge key (temporary, 2026-07-17):** the 2 tenants that existed when Jina went tenant-strict were bootstrapped onto one shared key so RAG/catalog search didn't break on deploy. Replace each with its own distinct Jina key when convenient — sharing one key means Jina cost still isn't separated per client, defeating the point.
- **GPT-5 family reasoning params are generation-specific and mutually exclusive** (`openai_client.py`): needs `max_completion_tokens` not `max_tokens`, and rejects non-default `temperature`. `reasoning_effort` must be `"minimal"` for the original gpt-5/gpt-5-mini/gpt-5-nano family (`"none"` 400s there) but `"none"` for dotted point releases like gpt-5.1/gpt-5.4 (`"minimal"` 400s there instead) — branch on `model.startswith("gpt-5.")`. Get this wrong and gpt-5-nano doesn't error, it silently burns its whole token budget on hidden reasoning and returns an empty string.
- **Gemini 3.x chat models default to `thinking_level: "medium"`** (`gemini_client.py`'s `generation_config`) — on `gemini-3.5-flash` this ate most of a 300-token reply budget on the hidden thought step, live-tested to either 30s-timeout or return text truncated mid-sentence. Set to `"minimal"` on both `gemini_chat_completion`/`gemini_chat_completion_with_tools`. `gemini-3.1-flash-lite` shares the same default but is fast enough it doesn't visibly show the problem — don't assume it's exempt if you change token budgets later.
- **`gemini-2.5-flash-preview-tts` is the current `DEFAULT_GEMINI_TTS_MODEL` (2026-07-17, reverted for cost — ~half the price of `gemini-3.1-flash-tts-preview`).** It hard-400'd ("Model tried to generate text, but it should only be used for TTS") earlier the same day, then worked again later with no code change — a preview-model flake on Google's side, not fixed by anything in this repo. Operator explicitly accepted the risk it could flake or get deprecated again with no warning; if it's next observed broken, swap back to `gemini-3.1-flash-tts-preview`. Don't assume today's working state is permanent.
- **`gemini-2.5-flash` shuts down 2026-10-16** (Google's own deprecation page, `gemini-3.5-flash` listed as replacement) — ruled out as the `analyze_call` model for this reason during the 2026-07-18 migration despite being otherwise well-suited; don't pick it for new work without rechecking that date first.
- **Gemini's `/v1beta/interactions` endpoint accepts audio/image/document input via a flat content-part shape** (live-tested 2026-07-18): `{"type": "audio"|"image"|"document", "data": <base64>, "mime_type": ...}` as a sibling to `{"type": "text", "text": ...}` in the `content` array — NOT the standard Gemini API's nested `inline_data` convention this endpoint otherwise superficially resembles. `"document"` (not `"file"`) is the type for PDFs; both `image` and `document` types were confirmed with real OCR output (exact verbatim text extraction), and `audio` was confirmed with a real transcription attempt. Used in `gemini_speech_to_text()`/`gemini_extract_document_text()` (`gemini_client.py`).
- **Gemini's formal JSON-schema response mode is broken on this endpoint** (live-tested 2026-07-18): `response_format: {"type": "object", "schema": {...}}` is accepted by request validation (the `type` enum is `object`/`string`/`array`/`boolean`/`text`/`image`/`audio`/`video`/`integer`/`number` — NOT `"json_object"`/`"json_schema"`, a different convention than OpenAI/Groq), but the model emits `{` followed by unbounded whitespace and never completes, regardless of `max_output_tokens` (tried up to 800). `gemini_chat_completion_json()` uses prompt-only "return JSON only" instead (same discipline `gemini_chat_completion` already relies on for plain replies), plus one retry on a parse failure since there's no hard guarantee here unlike Groq's `response_format={"type":"json_object"}`. Don't retry the schema mode without live-retesting first — it may get fixed on Google's end, but wasn't as of this test.
- **`maybe_single().execute()` returns `None` outright** (not an object with `.data=None`) on zero matching rows in this supabase-py version — guard `if x and x.data`, not just `if x.data`. `operator.py`'s `client_overview` hit this for a tenant with no `tenant_users` owner row (fixed 2026-07-17, see decisions/log.md); **still not swept across the other 20+ `maybe_single()` call sites in `operator.py`** (see active-backlog.md).

## Frontend performance pattern
- **Recipe:** `page.tsx` (async server component) fetches a seed via `lib/serverApi.ts serverFetchJson<T>(path, token, 2500ms)` (timeout-guarded → null on fail; MANDATORY or a cold backend white-screens SSR) → passes to a `<Route>Client.tsx` as SWR `fallbackData`. **Gate on DATA presence, not role** (seeded owners skip the spinner).
- `lib/api.ts apiFetch`: GET-only retry (network/timeout/502-503-504) + backoff + 30s GET timeout. **Mutations NEVER retry** (no double broadcasts/sends/assignments).
- Server components: `import type` for `@/lib/api` types (it pulls the browser supabase client).
- Render free tier sleeps after 15min → cold-start tail + **in-process APScheduler doesn't run**; keep-alive cron pings every 14min. One scaling caveat: externalize APScheduler before running >1 backend instance.

## Frontend styling conventions (Tailwind + `.input` utility)
- **`globals.css`'s `.input` class (padding/border-radius/focus-ring) and a Tailwind padding utility (`pl-9` etc.) on the same element are both single-class-specificity — which one wins is cascade-order-dependent, not guaranteed.** The existing convention in this codebase (e.g. `templates/page.tsx` search box) is to override `.input`'s padding via an inline `style={{ paddingLeft: ... }}` instead of a `pl-*`/`pr-*` Tailwind class, since inline style always wins regardless of stylesheet order. Follow this pattern rather than fighting the cascade with utility classes. Custom bordered controls that don't use `.input` at all (e.g. the select/dropdown wrappers on that same page) sidestep the issue entirely.
- **Brand color for interactive UI state is `primary` (violet, `#5b21b6`)**, not `emerald`/`green` — emerald is reserved for "Approved"/status-positive semantics elsewhere (template status badges, stat tiles). Active toggle/tab states in a control bar should use `text-primary`/`bg-primary`-family classes, not emerald, to stay visually consistent with what emerald already means in this app.

- **Language mirroring silent-switch bug: RESOLVED 2026-07-13 via post-reply check, NOT preemptive instruction** — `sarvam-30b` strongly anchors to the *script/style of its own immediately preceding reply*, and this beats ANY preemptive instruction tried, including deterministic per-turn tags, not just soft prompt wording. Two preemptive attempts both failed live: **Attempt 1 (2026-07-06)** reworded LANGUAGE RULE as a positive trigger — explicit switch requests 3/3, silent switches 0/3. **Attempt 2 (2026-07-13)** added `_latest_message_script_note()`, a deterministic per-turn Unicode-block script tag, tested at two prompt positions — still 0/6 on silent switches. **The working fix (Attempt 3, 2026-07-13)** abandoned preemption entirely: `_reply_script_mismatch()` checks the generated reply's script against the customer's latest message AFTER generation, before sending; on mismatch, ONE regeneration call fires. See decisions/log.md 2026-07-06 and active-backlog.md for full history.
- **Robust Multilingual Escalation Triggers (2026-07-07)**: `_HUMAN_REQUEST_RE` and `_AI_ESCALATION_RE` use flexible regex patterns (not static lists) to handle tenses, Romanized Indian languages (Tanglish, Hinglish, Tenglish), and native Indic scripts (Tamil, Hindi, Telugu, Kannada, Malayalam). **Gotcha**: Native Indic characters do not behave reliably with standard python regex word boundaries (`\b`) due to Unicode combining marks; native script patterns must omit `\b` check to match correctly.

### SIM call tracking — Android "Aira Sync" APK (`android/`, 2026-07-02)
- Companion native app, NOT part of the PWA/Next.js build. Purely a background sync daemon — no CRM UI, no dialer of its own. Reads `CallLog.Calls` via `ContentObserver` (near-real-time) + a 30-min `WorkManager` periodic fallback, filters to numbers matching the caller's assigned leads (`GET /calls/sim-lead-numbers`), and POSTs matches to `POST /calls/sim-cdr` with `X-Sync-Token` auth. `callers.sync_token` (migration 122) is the per-caller secret, minted via `POST /callers/{id}/sync-token` (owner-only).
- **Fail-closed privacy filter**: if the lead-numbers fetch fails, `SyncWorker.kt` returns `Result.retry()` and uploads nothing that round. Personal calls are never even attempted for upload — the filter runs before any network call to `/sim-cdr`.
- **Foreground service permission ordering is load-bearing**: `SyncService.onCreate()` MUST call `startForeground()` unconditionally first (Android kills a service that doesn't enter foreground promptly), THEN check `READ_CALL_LOG` and `stopSelf()` if missing. Registering the `CallLog.Calls` `ContentObserver` before checking the permission throws an unhandled `SecurityException` and crashes the whole app on first launch — this was a real shipped bug, fixed 2026-07-02. `AiraSyncApplication.onCreate()`/`BootReceiver` must also gate `SyncService.start()` behind a permission check, or the service (and its crash) fires on every app relaunch/reboot before setup is complete.
- **Distribution is live (2026-08-07)**: not on Play Store (`READ_CALL_LOG` is Play-restricted to default-dialer apps), sideload-only. Signed release APK hosted at the public Supabase Storage bucket `app-releases` (`aira-sync.apk`, migration `169`) — same URL every release, re-upload with `upsert: true` to ship an update. Signing key is `android/keystore/aira-sync-release.jks` + `android/keystore.properties` (both gitignored, PKCS12 so store/key password must be identical — keytool silently ignores a distinct `-keypass`). **This keystore is the app's permanent identity — if it's lost, every future update requires every device to uninstall/reinstall.** Download link + per-telecaller sync-token minting UI live on the client dashboard's Roles page (owner-only, gated on `callingProvider === "sim_basic"`) — deliberately NOT exposed to the telecaller's own view, same precedent as temp-password issuance (owner mints, relays out-of-band during phone setup).
- **Build-artifact trap (hit 2026-08-07)**: a build's file mtime is not proof it matches current source. The only APK that existed pre-2026-08-07 was built one minute after the Phase 2 recording-upload commit, two days *before* that feature was reverted — nobody had rebuilt it since, so it still shipped the abandoned Recordings UI calling a backend route that no longer existed. Before trusting an installed/built APK reflects `main`, check its build timestamp against the relevant commit dates (`git log -- android/`), especially after any revert.
- Double-count risk: unreconciled with the PWA cockpit's own `sim_started` row creation (see `sim-dialer.ts`/`useCallingCockpit.ts` above) — if a telecaller dials via both paths for the same call, two rows can result. See active-backlog.md.
- **Enrichment reconciliation is order-independent (fixed 2026-07-03)**: the lookup in `_ingest_sim_call` that matches a fresh APK sync to an existing PWA-created row is gated ONLY by `call_sid IS NULL` (not by `status IN (sim_started, initiated)`) — so it doesn't matter whether the wrap-up form or the APK sync completes first, they always converge on one row. The `updates` dict the APK path writes must stay hard-facts-only (`call_sid`/`status`/`disposition`/`duration_seconds`, outcome only if the human hasn't already tagged one) — never `notes`/`tags`/`quality_rating`/`manual_started_at`/`manual_ended_at`, which stay human-owned regardless of ordering.
- **Recording upload (Phase 2) was built, then reverted 2026-07-05** — see decisions/log.md for the full writeup. Root blocker: whether a phone auto-records calls at all depends entirely on which app is set as the **default dialer**. Google's Phone app (common default even on non-Pixel phones) gates recording behind a manual per-number whitelist (Play policy, region-gated) — it does NOT blanket-auto-record. OEM native dialers (MIUI's stock Dialer, etc.) DO auto-record unrestricted, because they're privileged system apps — this is also why the known-path folder list (`/storage/emulated/0/MIUI/sound_recorder/call_rec` etc.) only ever gets populated when the OEM's own dialer is active, not Google's. Building an in-app recorder instead isn't a viable workaround: Android has restricted the `VOICE_CALL`/`VOICE_UPLINK`/`VOICE_DOWNLINK` audio sources to privileged/system apps only since roughly Android 9/10, which is exactly why standalone recorder apps work on Xiaomi/MIUI but not stock Android/Pixel. Any future revival of this feature needs a per-telecaller onboarding check (confirm default dialer + its native recorder's auto-record setting) before assuming recordings will exist to harvest — Phase 1 (call-log metadata only) does not depend on any of this and is unaffected.

## Channel settings save path (app_settings.py PATCH /api/v1/settings/)
- **Save handlers for every channel (WhatsApp/Instagram/Facebook/Telegram) MUST be DB-write-only — no outbound HTTP calls.** WhatsApp/IG/FB saves always were (upsert credentials, set `{channel}_status="configured"`, return in milliseconds). Telegram's save handler was the one exception: it called `setup_telegram_webhook()` synchronously inside the PATCH request, making a live outbound call to `api.telegram.org/bot{token}/setWebhook` before responding. On Render's free tier this occasionally hung/timed out long enough that the proxy killed the connection before any HTTP response reached the browser — the frontend's `fetch()` never got a response at all (native rejection, not an HTTP error), so it fell back to a generic "Cannot reach the server" message. **Fixed 2026-07-02** by moving `setup_telegram_webhook()` out of save entirely; save now only validates the token format (`\d+:[A-Za-z0-9_-]+` regex) and persists `telegram_status="configured"`, matching the other three channels exactly. The outbound `setWebhook` call now only happens in `POST /activate` (user-initiated "Validate & Activate" button click), where a slow/failed Telegram API call is an expected, bounded, user-visible wait — not a silent request killer.
- **Diagnostic trap**: a `net::ERR_FAILED` / "Cannot reach the server" browser error with NO HTTP status code (not 400/502/504) means the TCP connection died before any response — this is NOT a CORS rejection even if the browser's console prints a CORS-looking message (Chromium shows generic CORS text for any cross-origin connection failure since it has no response headers to inspect). Rule out CORS by checking whether *other* channels' saves succeed from the same origin/session — if WhatsApp/IG/FB save fine but Telegram doesn't, the failure is channel-specific code, not CORS config. This exact confusion cost several debugging rounds before the user pointed out the differential symptom.
- **`get_setting()` (`config_dynamic.py`) previously conflated "not configured" with "DB read failed."** A transient Supabase disconnect (httpx `Server disconnected`, a dropped pooled keep-alive connection) during a `get_setting` call was silently swallowed and returned `None` — indistinguishable from a genuinely-unset credential — and that `None` got cached for `_TTL` (60s), so `_creds()` in `meta_cloud.py` would raise "Meta credentials not configured. Set them in Settings." (and fire the owner's `system_error` notification) even when `app_settings` had valid, current credentials. **Fixed 2026-08-07**: `get_setting` now retries once immediately on any read exception (clears most transient blips before they're ever visible to the caller) and only writes to `_CACHE` on a confirmed read — a failed read is never cached, so the next call re-hits the DB instead of serving a false negative for the rest of the TTL window. Diagnosed by cross-referencing the `app_notifications` row's timestamp against Render logs for that exact second — the `get_setting(...) DB read failed: Server disconnected` warning was right next to the misleading error.

## Web Push

## Callback notifications (services/callback_notifications.py — claimable-only)
- **1-min job `callback-notifications`** replaced the old `callback-reassignment` auto-move (2026-07-01). Two passes: (1) DUE — `scheduled_for <= now` & `due_notified_at IS NULL` → push `callback_due` to the lead's **assigned** caller; (2) CLAIMABLE — `scheduled_for <= now - threshold` & `claimable_notified_at IS NULL` → `notify_callback_claimable` to the configured audience, **with NO shift/availability check** (out-of-shift owners included). Guard columns are set on fire (once-only); `reschedule_callback` nulls both to re-arm. **There is NO auto-reassignment** — overdue callbacks are pulled manually via `POST /leads/{id}/takeover` (still CAS-guarded), which now also pushes the previous owner (`callback_taken_over`).
- **Threshold + audience are config:** `notification_config.claimable_threshold_minutes` (default 15); `claimable_audience` ∈ `telecallers_and_admin | telecallers_only | admin_only | specific` ("specific" uses `claimable_caller_ids`, owner NOT auto-added). Claimable recipients = enrolled callers (`active=True`, **ANY status** — push must reach app-installed-but-logged-out callers via their `push_subscriptions` row) + owner, minus the current owner.
- **Gotcha:** the migration-122 guard columns (`due_notified_at`/`claimable_notified_at`) MUST exist before the job runs, or the `.is_(...,"null")` filters error every tick (caught per-tenant, logged, no-op). v1 limitation: push `tag` falls back to the bare type (no `dedupe_lead_id`), so simultaneous same-type pushes can collapse on the device lock screen — the in-app bell keeps all.

### Operator Console — Itemized Subscriptions (2026-07-04, client-driven cart — supersedes the 2026-07-02 admin-assigns-one-plan model above)
- **The model changed from "admin assigns a tenant one plan" to "tenant builds their own itemized cart, admin approves it."** `tenant_subscriptions.plan_id` still exists but is now just a display-only "started from this package" pointer — **never authoritative for entitlements**. The source of truth is `tenant_subscription_items(tenant_id, feature_key, quantity, unit_price_snapshot)`, one row per purchased feature_key. `resolve_entitlements(db, tenant_id)` keeps the exact same signature/return shape (`{"features": [...], "quotas": {...}}`) but now reads `tenant_subscription_items` joined against `feature_catalog.depends_on`/`usage_metric`/`included_qty`, not `plans.feature_keys`/`quotas`. `get_purchased_quantity(db, tenant_id, feature_key)` is new — sums quantity for one feature_key, used by hard-cap checks.
- **`feature_catalog.depends_on`** (existed since migration 123, never wired up until now) is what turns a purchased SKU into a bundle of internal flags: e.g. buying `outbound_messaging` also enables `whatsapp`/`broadcast`/`templates`/`auto_reply`/`human_handover`. The 8 client-facing sellable SKUs are `inbound_messaging`, `outbound_messaging`, `telecalling_sim`, `telecalling_telecmi`, `bulk_lead_upload`, `telecaller_seats`, `numbers_pool`, `notifications` — everything else in the 43-row catalog is an internal flag, never priced/purchased directly.

Callers must call `check_quota()` **before** attempting the action and `meter()`/`increment_usage()` **after** it succeeds — they're two separate steps now, not one. Wired into 4 places: `team.py::invite_member` (against `get_purchased_quantity(..., "telecaller_seats")`, a live COUNT comparison, not a period counter), `numbers.py::create_phone_number` (same pattern against `numbers_pool`), `ai_reply.py::generate_reply` (against `ai_reply` metric, fails safe — returns early like the existing blocked-lead branch, webhook callers still get their normal 200), `calls.py::initiate_call` (against `call_minute`, checked at initiation since minutes are only known after a call ends via the TeleCMI CDR webhook). **`broadcast_executor.py` is deliberately NOT gated** — outbound message sends stay track-only `meter()`, by explicit user scope decision mid-build.
- **Package price is always computed, never hand-typed.** `plans.discount_percent` (new column) + `plans.feature_keys` (same column, repurposed: now `[{feature_key, quantity}]` instead of a flat key list) feed `_compute_package_price()` in `operator.py`, which resolves each item's price as `unit_price if not null else monthly_price` (mirrors `subscription_requests.py::_price_for_item`) — **do not just read `monthly_price`**, `telecaller_seats`/`numbers_pool` have `monthly_price=0` and are priced entirely via `unit_price × quantity`.
- **Feature Store is gone entirely** (not just repurposed this time) — `client/[id]/views/feature-store.tsx` deleted, replaced by a read-only `entitlements.tsx` (current `tenant_subscription_items` + `tenant_subscriptions.status`, no plan-assignment action of any kind). The old `GET/PATCH /clients/{tenant_id}/subscription` plan-assignment routes are deleted from `operator.py`. Assigning entitlements to a tenant now only happens by approving a `subscription_requests` row (`POST-adjacent` `PATCH /operator/subscription-requests/{id}`), never by a direct admin action on the tenant.
- **New tenants start with NO `tenant_subscriptions` row at all** (gated — the frontend shell treats a missing row as `status: "none"`). `create_client` no longer creates one, no longer seeds `enabled_features`/`tenant_usage_counters` from a plan. - **`ClientLayout.tsx` gates the ENTIRE dashboard** on `GET /api/v1/subscriptions/me`'s `status` field — `"none"`/`"pending_approval"` renders only the full-page Subscriptions cart (no sidebar, no other route reachable regardless of URL), `"active"` renders normally. Fails open to `"active"` on any fetch error (network blip, cold start) — a broken subscriptions endpoint must never lock out an already-approved tenant.
- **Sidebar Toggle and Calling Provider Sync (Migration 129)**: Approving a subscription request or calling `sync_client_toggles(db, tenant_id)` recomputes entitlements and synchronizes client console toggles (`enabled_features` in `tenants`) and `calling_provider` in `telecalling_config`. Old billing-derived keys are automatically removed to mirror the active subscription items, while non-billing-derived keys (e.g. `analytics`) survive untouched. Standalone `notifications` is bundled directly into `inbound_messaging` and `outbound_messaging`. Testing this requires passing `db` to `get_telecalling_config` and `save_telecalling_config` (which now accept an optional `db` parameter to prevent unit tests from triggering live Supabase connections via `get_supabase()`).

## WhatsApp templates & admin notifications (2026-07-03)
- **`notification_config.py`'s merge is hand-rolled per-key, not a generic deep merge.** `get_notification_config` explicitly special-cases `events`/`quiet_hours`/`whatsapp_notifications` by name and whitelists specific scalar keys from the stored row. A new nested config key will NOT survive automatically — it must be added to `_NOTIFICATION_CONFIG_DEFAULT`, the merge block in `get_notification_config`, AND `NotificationConfigIn`'s Pydantic schema + `update_config`'s explicit persistence dict, or it's silently dropped (Pydantic ignores unknown fields by default; the PUT handler only writes keys it explicitly lists).
- **`growth.py::record_stage_event` is a plain sync function with no `BackgroundTasks` access**, called inline from ~9 request-path call sites (`leads.py`, `calls.py`, `facebook.py`, `instagram.py`, `telegram.py`, `upload.py`, `webhook.py`, `ai_reply.py`) — several run inside the user-facing `PATCH /leads/{id}` request. No Celery in this codebase. Fire-and-forget pattern used: `asyncio.get_running_loop().create_task(...)` guarded by `try/except RuntimeError` (no-op + log if no loop), with the task held in a module-level `set()` (`task.add_done_callback(set.discard)`) — otherwise it can be garbage-collected mid-flight, a well-known asyncio gotcha.
- **For single/low-volume `send_template_message` calls, pass only `tenant_id`** (not `phone_number_id`/`access_token`) — `meta_cloud._creds()` resolves the tenant's primary WhatsApp number internally. This is the pattern `reengagement_service.py::_send_step_template` already uses. Only bulk broadcast senders (`broadcast_executor.py`, `upload.py`) need the heavier `outbound_router.get_best_number`/`increment_send_count` pair for per-number rate/quality tracking — don't reach for that pair on a low-volume alert path.
- **`process_due_reengagements` must stay batched (fixed 2026-08-06, was N+1)** — it runs every 1 minute via the `reengagement-rules` APScheduler job, across every tenant/lead. A per-lead `reengagement_logs` existence check (and, on the broadcast branch, a per-lead `leads` fetch) was firing one Supabase round-trip per lead per tick — 100 sequential calls in 10s observed in Render logs — which saturated the Starter instance's 0.5 CPU every tick and starved the `/health` check into repeated Render flap (instance-failed/recovered) even though the plan had zero free-tier sleep involved. Use `_already_processed_lead_ids()`/`_fetch_leads_by_id()` (batched `.in_()` lookups) and keep delay/segment/source filtering in-memory *before* any DB call — don't reintroduce a per-lead loop here. See decisions/log.md 2026-08-06 entry.
- **`message_templates` has a `UNIQUE(tenant_id, name)` constraint checked in app code before Meta is ever called** (`templates.py::create_template`, line ~91). A POST with a name that already exists locally 409s regardless of that row's `status` — including a row that failed at Meta and never got a real `meta_template_id`. Repair path is PATCH (only allowed when `status` is `REJECTED`/`PAUSED`) or DELETE+recreate, never a second POST with the same name.
- **`whatsapp_notifications.recipient_phones` must never overlap with a real/test lead's own phone number in the same tenant (learned 2026-07-06)** — the admin segment-change alert sends to every number in `recipient_phones` whenever ANY lead crosses into a `target_segments` value, with the LEAD's name filled into the template. If an admin/tester's own number is both the recipient AND a tracked lead, they'll receive alerts about *other* leads' (or their own) segment changes on the same WhatsApp thread they use for customer-side testing — reads exactly like a broken duplicate-auto-reply bug but is pure config. Also confirm `template_id` actually points at internal-facing admin copy ("Lead {{1}} just moved to {{2}}") — `aira_connect` (the default in at least one tenant) is a customer-facing "thanks for reaching out" template and produces nonsensical copy when used for this alert.
- **Meta template hard rules learned from live rejections** (Graph API `error_subcode`): `2388299` = a `{{n}}` variable can't be the first or last token of the body — trailing punctuation right after the last variable (e.g. `{{4}}.`) is NOT sufficient, Meta wants real trailing text/words. `2388293` = "words ratio" limit on variable count vs. body length — formula is undocumented; treat as a soft heuristic (roughly 6+ words per variable), not a hard rule. Positional `{{n}}` must be numbered sequentially from 1 with no gaps. All three are now validated both client-side (`frontend/app/dashboard/templates/types.ts::validateTemplateBody`/`templateBodyWarning`) and server-side (`templates.py` Pydantic validators on `CreateTemplate`/`UpdateTemplate`) — the deterministic two are hard-blocked, the ratio one is a warning only.

## Ad attribution — Meta CTWA vs Google tag (webhook.py, 2026-07-05)
- **Two independent attribution mechanisms feed the same `leads.ad_campaign_id` + `ad_campaigns` table**, both in the WhatsApp webhook's inbound loop, Meta block first then Google:
  1. **Meta CTWA/referral** — `msg.get("referral")` with `source_type=="ad"`. ONLY Meta populates this (Click-to-WhatsApp, and the parallel FB/IG DM webhooks). Google/organic messages never have it.
  2. **Google tag** — `parse_google_ref(body)` looks for a `[GADS:<slug>]` tag in the message text, injected via a `wa.me?text=` pre-fill on the Google ad. This is the ONLY way Google traffic gets attributed — Google cannot send Meta's referral object.
- **Order + guard is load-bearing**: the CTWA block sets a local `ad_attributed` bool; the Google block runs `if not ad_attributed` AND only writes when `leads.ad_campaign_id` is currently null. So Meta always wins if both are somehow present, and a repeat tagged message never re-stamps or duplicates the campaign. Don't reorder these or drop the null-check — you'll double-count or let Google overwrite a Meta attribution.
- **Tag format lives in ONE file** (`services/google_ads_attribution.py`) used by BOTH the parser (webhook) and the link generator (`/inbound-leads/google-link` endpoint + UI modal). If you change the regex, the generator's `[GADS:...]` output must change with it — the `test_build_link_round_trips_through_parser` test is the tripwire. `external_campaign_id` is namespaced `google:<slug>` to avoid colliding with Meta numeric ad ids in `get_or_create_campaign`'s external-id lookup.
- **`gclid` is captured but inert** — parsed and logged, not yet resolved against the Google Ads API. Real Google spend / cost-per-lead is NOT populated (unlike Meta where `ad_campaigns.spend_inr` can be set). The comparison-table USP shows lead *counts* per platform today, not cost, until the gclid→Ads-API reconciliation is built.
- **Attribution depends on the client using the generated link.** A bare `wa.me` number with no tag → lead stays `organic`, Google uncredited. This is why the generator is a UI button (no hand-typing) — but it's still a client-onboarding dependency, not something the platform can enforce.

## Subscription billing addendum - flat modules, unlimited phase (2026-07-05)
- **Supersedes the earlier 2026-07-04 cap wording in this file.** During the current phase, `tenant_usage_counters.included` is informational only. `check_quota()` must return false only when an explicit `hard_cap` exists and the delta would exceed it. Missing rows, `included=0`, and old finite included values must not block AI replies, telecalling, messaging, seats, or phone numbers.
- **Flat-price modules**: `inbound_messaging`, `outbound_messaging`, `telecalling_sim`, `telecalling_telecmi`, and AI tier rows are subscription entitlements, not metered usage products. Treat `monthly_price` as the product price. Do not add per-message, per-call, or per-reply enforcement unless the product decision changes again.
- **Quantity concepts are not enforcement yet**: AI tokens may still be shown/tracked, but the AI-reply path should not hard-block on included counters while this unlimited phase stands. `hard_cap` remains the escape hatch for a deliberate client-specific stop. **Telecaller seats and numbers pool are the exception — see the 2026-07-31 addendum below, which supersedes this bullet for those two.**
- **Proration**: Add-on requests for existing tenants charge only the remaining fraction of their current anchored monthly billing cycle. For newcomers (initial requests), they specify custom start/end dates (defaulting to 15 days), and the backend calculates proration as `duration_days / 30.0` for all item line totals and total request amounts. When approved, these custom dates become the active `period_start` and `period_end` of `tenant_subscriptions` to anchor their initial cycle.
- **Catalog row editing & column visibility**: The operator Pricing Catalog edits catalog rows on a daily-price-first basis (monthly = daily × 30). For flat modules (`unit_price === null && included_qty === null`), the operator console hides the `Unit` and `Included` inputs (rendering empty spacer columns), providing only the daily rate editor.

## Telecaller seats & numbers pool: hard enforcement restored (2026-07-31)
- **Supersedes the "quantity concepts are not enforcement yet" bullet above, for `telecaller_seats` and `numbers_pool` only** (AI tokens and the flat-price modules are unaffected — still unlimited/informational). The client explicitly asked for these two to be capped at the approved/purchased quantity again.
- **Telecaller creation now lives entirely on the Roles page** (`POST /api/v1/rbac/users` in `routes/rbac.py`), not Teams. ## Numbers pool: Meta-account-driven bulk sync + quota locking (2026-08-06)
- **New discovery path, separate from the manual-add block above**: `POST /api/v1/numbers/sync-from-meta` (tenant-scoped) pulls every number registered on the tenant's connected Meta WABA via `meta_cloud.list_waba_phone_numbers` (`{waba_id}/phone_numbers` Graph edge) and imports any not already in `phone_numbers`, **regardless of `numbers_pool` quota**. Manual single-number `POST /api/v1/numbers` is unchanged and still hard-blocks at quota (`_numbers_pool_limit`/`numbers_pool_limit` in `numbers.py`/`numbers_pool.py`) — only the bulk Meta sync is allowed to bring in more than the tenant has purchased, landing the excess **locked** instead of rejecting it.
- **Locking is computed live, never stored** — `numbers_pool.py::compute_unlocked_ids(rows, limit)` is a pure function: `role="primary"` always wins a slot; the remaining `limit - 1` slots go to non-primary rows oldest-first by `created_at`; **if no primary exists yet, nothing is unlocked, regardless of `limit`** (oldest-first only ever fills slots *in addition to* a guaranteed primary slot). This means a brand-new tenant syncing 3 Meta numbers against a 1-number quota sees all 3 locked until they explicitly click "Set Primary" on one — the system never auto-picks by arbitrary Meta response order. It also means a subscription **downgrade** takes effect on the very next `GET`/routing decision with no re-sync needed, and the previously-primary number specifically (not just "the oldest") is what survives, since primary is the anchor, not age.
- **`get_unlocked_number_ids(db, tenant_id)`** (DB wrapper around the pure function) is the single shared choke point — used by `GET /api/v1/numbers/` (`locked` per row), `PATCH /{id}` (blocks `status="active"`/`paused_outbound=false` on a locked number; **`role="primary"` is always allowed** — it's the unlock action itself, swapping which number holds the slot), and `outbound_router.get_best_number()` (excludes locked candidates from real message routing — this is the layer that makes locking actually bite, since `get_best_number` picks among **any** `status=active` number today, not just `role=primary`). If you add a new place that selects a phone number for anything quota-sensitive, route it through this helper too, or a locked number could silently be used.
- **Deliberately NOT locked**: `failover.py`'s `handle_quality_red` can still auto-promote a locked standby to primary during a quality-red outage — once promoted it legitimately wins the slot, and losing this would mean a client could end up with zero working numbers mid-outage. Inbound messages to a locked number are received/logged normally; only outbound *selection* is gated.
- **Quality-value format gotcha**: the bulk sync uses a **separate** `_WABA_QUALITY_MAP = {"GREEN": "green", "YELLOW": "yellow", "RED": "red"}` in `numbers.py`, not the pre-existing `_QUALITY_MAP = {"HIGH": "green", "MEDIUM": "yellow", "LOW": "red"}` that the older single-number `sync_number_from_meta`/`get_number_quality` path uses. The WABA `phone_numbers` list edge and `webhook.py`'s `phone_number_quality_update` handler / `failover.py`'s `QUALITY_MAP` all agree on GREEN/YELLOW/RED — `_QUALITY_MAP`'s HIGH/MEDIUM/LOW looks like it may be wrong for the endpoint it's applied to (see active-backlog.md; not fixed here, pre-existing and out of scope for this change).
- **Full design/plan**: `docs/superpowers/specs/2026-08-06-meta-numbers-pool-sync-locking-design.md`, `docs/superpowers/plans/2026-08-06-meta-numbers-pool-sync-locking.md`.

## Frontend CSS gotcha: absolute-positioned icon button inside a `relative` wrapper around an `<input>` (2026-07-31)
- `CalendarPanel.tsx`'s To-Do add-input had its `+` submit button (`absolute top-1/2 -translate-y-1/2`) visually centered too low, hanging below the input's rounded bottom edge. Cause: `<input>` is an inline-level replaced element, so a `relative` wrapper (`<form>` here) around a bare `<input>` inherits an invisible baseline "strut" from the font's line-box, making the wrapper's height taller than the input's own visible box — with the extra space landing below it. `top-1/2` centers against that taller invisible box, not the visible input. Fix: add `flex` to the wrapper (`className="relative flex group"`) so its height is driven purely by the input as a flex item, with no strut. Also fixed in the same pass: the input had `border-none` but no `outline-none`, so the browser's native focus outline (a heavy black rectangle) showed through instead of the intended `focus:ring-2 focus:ring-primary/20`. **Watch for this same pair of bugs anywhere else in the codebase that positions an absolute icon/button over a bare `<input>` inside a plain `relative` (non-flex) wrapper.**

## Frontend CSS gotcha: `100dvh`-relative `max-h` on an absolutely-positioned popover (2026-08-07)
- `AdPerformanceTab.tsx`'s "Columns" metrics popover (21 metrics) used `max-h-[calc(100dvh-7rem)]` on the dropdown panel, sized as if the panel started at the very top of the viewport. It doesn't — it's `absolute`-positioned under the trigger button, wherever that button sits on the page — so the calc let the panel claim far more height than the space actually below the button, and its lower rows ended up clipped/hidden depending on scroll position, with only a thin internal scrollbar as a hint anything was cut off. Fix: swapped to a fixed `max-h-[22rem]` (~352px, header + ~4-5 rows visible) with the existing `overflow-y-auto` on the inner list — deterministic regardless of where the trigger sits on the page. **Prefer a fixed rem cap over `dvh`-relative sizing for any absolutely-positioned dropdown/popover whose trigger isn't pinned to the viewport edge; `dvh` math only works for panels anchored at a fixed viewport position.** One other `calc(100dvh...)` usage exists in `frontend/app/dashboard/conversations/page.tsx:250,265`, but that's sizing a top-level page container to the viewport (a different, valid use), not a popover — not the same bug.

## Client RBAC roles and user management (2026-07-12)
- RBAC is tenant-scoped through `tenant_roles` plus `tenant_users.role_id`. A user has exactly one role. Owners remain legacy `tenant_users.role='owner'` and implicitly receive all permission keys; non-owner users resolve their role through `resolve_permissions()`.

The frontend sidebar, route access, and backend `require_permission()` must all read from this same resolved permission set.

Don't conflate them — different scope, different backend (`meta_ads.py` router vs `inbound_leads.py`).
- **The 3 tabs live in the shared `AppHeader`, not in the page**, driven by the `?tab=` query param exactly like Outbound Leads: no `?tab` → Ad Performance (default), `?tab=create` → Create, `?tab=analytics` → Analytics. `MetaAdsClient` reads `useSearchParams()`; the page renders no title/pills of its own. To add/rename a tab you touch BOTH the `AppHeader` Meta Ads pill block AND `MetaAdsClient`'s tab resolver.
- **`ads_management` is PENDING Advanced Access (submitted, not granted).** Everything in `meta_ads_manager.py` (create campaign/adset/creative/ad, status toggle, budget edit) works only against **Aira's own test ad account** on Standard Access until approval. **No code changes when it lands** — only which ad accounts are authorized targets. Also requires `pages_manage_ads` + a Facebook Page id (`GET /act_<id>/promote_pages`, stored on `ad_campaigns.page_id`). The payload builders + persistence are unit-tested; the live Meta round-trip is unverified in CI (see active-backlog.md).
- **CBO invariant**: budget (`daily_budget`/`lifetime_budget`) + `bid_strategy` go on the **campaign**, never the ad set. `build_adset_payload` deliberately has NO budget field (`meta_ads_payloads.py`, asserted in `test_meta_ads_payloads.py`). This is why the Ad Performance table's inline budget-edit is campaign-level only, and edits are disclosed as "shared across the whole campaign."
- **Money direction is paise (×100) on WRITE, rupees (÷100) on READ.** The sync (`sync_campaign_meta`) divides Meta's minor-unit budgets by 100 when storing; `build_campaign_payload`/`update_campaign_budget` multiply INR by 100 when sending. Get the direction wrong and budgets are off by 100×.
- **Objective is locked to Click-to-WhatsApp** across the whole Create flow: campaign `OUTCOME_ENGAGEMENT`, ad set `destination_type=WHATSAPP` + `optimization_goal=CONVERSATIONS` + `billing_event=IMPRESSIONS`, creative CTA `WHATSAPP_MESSAGE` + link `https://api.whatsapp.com/send` + `page_welcome_message.autofill_message.content` = the pre-filled greeting. Adding another objective later means extending the Objective step + objective-specific fields; the wizard/budget/publish scaffolding doesn't change.
- **`sync_campaign_meta` failure must NOT fail the verbose sync's `ok` status** (fixed during Plan 1 build). Campaign-metadata enrichment is best-effort (log-only in both `sync_tenant_ad_insights` and `_verbose`); if it were appended to `row_errors` it would make the "Sync Now" button report a false error even when all insight rows wrote fine. Its unit test monkeypatches `_fetch_campaigns` to stay hermetic.
- **Reporting rolls up from per-creative rows, no separate per-level insight tables.** `build_account_performance(level=campaign|adset|ad)` fetches at ad level and groups via `roll_up_rows`; campaign status/budget come from `ad_campaigns` (populated by `sync_campaign_meta`), ad-set names from the denormalized `ad_creatives.meta_adset_name`. The `ad_sets` table (migration 149) exists to persist Aira-*created* ad sets, not to drive reporting.
- **Live Supabase project ref is `ayftynkgmfkaqmmnlmoc`** — the backend `.env`'s `SUPABASE_URL` shows a different, DNS-unreachable ref; the MCP-connected project is the real one. Confirmed by the presence of the migration-147 ad tables there.

## Meta Ads reporting surface (2026-08-02)
- `/dashboard/meta-ads` is the sole Click-to-WhatsApp Ad Performance surface; `/dashboard/inbound-leads` is leads-only. The old Meta Ads manager route, API client, and Create/Performance/Analytics components were removed; the report API remains under `inbound_leads.py` because it is the attribution backend.
- Daily insights are additive for spend, impressions, and clicks, but not reach. The sync merges Meta's `last_30d` completed-day response with its `today` response so live same-day delivery is visible after Sync now. `build_creative_performance()` uses Meta's aggregate ad-level reach for the selected `time_range`; on a Meta failure it logs and temporarily falls back to stored daily reach rather than hiding the report.

## Inbound Ad Performance account scope and attribution semantics (2026-07-30/31, migrations 153+154)
- The Inbound Leads **Ad Performance** tab is scoped to the tenant's currently configured `meta_ads_account_id` and to ad sets whose Meta `destination_type` is exactly `WHATSAPP`. The scope is local to this report: the neighboring Leads tab still includes WhatsApp, Instagram, Facebook, and Telegram.
- `ad_creatives`, `ad_campaigns`, and `ad_insights_daily` carry `meta_ad_account_id`; creatives also carry `is_click_to_whatsapp`. The sync fetches ad-set metadata before writing insights and records `meta_ads_last_sync_at`, `meta_ads_last_sync_count`, and `meta_ads_last_synced_account_id`. Migration 154 adds ad-set daily/lifetime budgets; report budget falls back to campaign only when the ad set owns no budget.
- Meta CTWA attribution does **not** depend on the visible pre-filled message text. `webhook.py` uses the inbound message's invisible `referral.source_id` (Meta ad id), so a customer can replace the pre-fill with `Hi` and still be attributed when Meta supplies the referral. If the referral is absent, the message is stored but cannot currently be assigned to a Meta creative.
- Current `messages` in `services/ad_performance.py` means unique lead rows with `attributed_ad_creative_id`, not individual inbound messages or ad-entry events. The webhook only sets that creative field while NULL. Therefore repeat interactions by an existing lead do not produce a second Aira conversion and a later Ad B does not replace first-touch Ad A. Date filtering is also based on `leads.created_at`.
- The correct future model is message-level `ad_attribution_events`: keep one lead per phone, but create one idempotent attribution event per referral-bearing inbound message, with method `meta_referral`, `tracking_code`, `manual`, or `unattributed`. A short per-ad tracking code in the pre-filled text can recover attribution when referral metadata is missing, but cannot help if the customer deletes the code or the entire webhook never arrives.

## Analytics page: IST windowing opt-in, and the post-2026-08-01 tab structure
- **`_resolve_window()` (`analytics.py`) defaults to UTC calendar days; `Asia/Kolkata` is opt-in via a `calendar_timezone` param (query alias `timezone`).** `/compare` was always IST-aware; `/messaging` and `/inbound` were not until 2026-08-01, so they silently bucketed late-evening IST activity into the wrong UTC day. If you add a new analytics endpoint that windows by day, thread this same param through rather than hardcoding UTC — check `/compare`'s existing `IST_OFFSET` usage as the reference implementation, not `datetime.now(timezone.utc)` from an older endpoint.
- **The Analytics page is no longer 5 tabs.** `OverviewTab` was deleted (2026-08-01) — Overview's content was folded into `CompareTab.tsx`, which is now a controlled component (`range`/`comparison` passed as props from `AnalyticsPage`, no local picker state). If you're looking for "the funnel" or "New leads/Conversions/Cost per lead" cards, they're gone from Overview's old shape — the funnel survives as `buildFunnel()` in `overviewPresentation.ts`, rendered inside `CompareTab`; the KPI cards and trend line were deleted outright as duplicates of Compare's own stat cards and segment-mix chart, not migrated.
- **One shared `range`/`comparison` state lives in `AnalyticsPage` (`page.tsx`), not per-tab.** `Compare`/`Channels`/`Inbound` all read the same `range`; only the merged Overview/Compare tab also uses `comparison`. Templates has no date range at all (`templatePerformance()` takes none) and keeps its own local range state, separate from the shared one. **Exception (2026-08-07): `ChannelsTab` now also renders its own `RangePicker` bound to the shared `range`/`setRange`** — not local state, just rendered inside `ChannelsTab`'s own merged filter panel alongside the channel selector, at the client's explicit request to put Channel + Period on one line. This is not a reintroduction of the per-tab duplication the 2026-08-01 consolidation removed (state is still shared/lifted); don't read it as license to give other tabs their own independent range state.
- **Tab order is Overview → Channels → Inbound → Templates (2026-08-07), and the tab strip itself now lives in `AppHeader.tsx`**, not rendered inline in `page.tsx` — styled/sized to match the Outbound Leads header pills (`components/AppHeader.tsx`, keyed off `pathname === "/dashboard/analytics"`). `page.tsx` only reads `?tab=` via `useSearchParams`; it no longer owns tab-switching UI or the `TABS` array (deleted).
- **Period/Compare (and, on Channels, the channel selector) are collapsed behind a single "Filters" toggle**, not shown inline by default (2026-08-07). `AnalyticsPage` owns one `showFilters` boolean, threaded down as `filtersOpen`/`onToggleFilters`/`hasActiveFilters` props to `CompareTab`/`ChannelsTab`/`InboundTab`. Each tab's action column renders buttons in a fixed order: **Refresh → Filters → Download CSV**, via the shared `components/analytics/FiltersToggleButton.tsx`. `ChannelsTab` is the one tab that does NOT receive the page-level generic "Period Filters" panel (`page.tsx` explicitly excludes `activeTab === "channels"`) — instead it renders its own single merged panel (Channel selector + Period, one row) off the same `filtersOpen` state, so there's exactly one "Filters" button/panel per tab, never two. Templates keeps its own independent local filter toggle (different concept — reporting period only, no page-level state).
- **Frontend CSS gotcha: a `space-y-*` wrapper still adds top margin to the next real DOM child even when a collapsible sibling above it is animated to `max-h-0`/0 opacity.** Tailwind's `space-y-n` sets `margin-top` on every child after the first via a `:not(:first-child)` selector — it doesn't know or care that the first child is visually collapsed, so a "closed" filter panel still pushed the KPI cards down by the full `space-y` gap (hit on `ChannelsTab`, 2026-08-07). Fix: don't wrap a section containing a collapsible panel in `space-y-*`; give each section its own explicit `mb-*`/`mt-*` instead so collapsed state can actually reach zero height.
- **The "Needs attention" stale-hot-leads panel and `GET /analytics/hot-leads-stale` are gone entirely** (frontend + backend + tests), removed 2026-08-01 at the client's request. If asked to add a "who needs a reply" surface again, don't resurrect the old one from git history uncritically — it was removed for being non-actionable (10 identical "no reply since last message" rows), and the client's stated preference is for it to live in Conversations where the reply action happens, not in Analytics. See active-backlog.md.
- **`Download` icon / CSV export lives only on the merged Compare tab now** (`api.analytics.exportCompareCsv`), not duplicated elsewhere. A prior merge pass accidentally dropped this button as unrelated collateral damage and it had to be restored via code review — if refactoring `CompareTab.tsx` again, grep for `exportCompareCsv` afterward to confirm the button survived.
