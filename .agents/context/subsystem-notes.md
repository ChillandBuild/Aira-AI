## Deployment (Render)
- **`autoDeploy` was observed `no` on the `aira-ai-5tfr` web service as of 2026-07-02**, contradicting the 2026-06-06 decisions-log entry "Render Auto-Deploy ON." Don't assume `git push origin main` puts a change live — check `mcp__render__list_deploys` for the actual live commit (status `"live"`) before verifying or debugging "why isn't my fix working in prod." Deploys are currently manual/API-triggered.
- **Forcing a redeploy without dashboard access**: `mcp__render__update_environment_variables` (merge mode, e.g. re-setting `FRONTEND_URL` to its current value) triggers Render to pull latest `main` and redeploy even with `autoDeploy: no` — this is the only MCP-available way to redeploy; there's no direct "trigger deploy" tool. The auto-mode permission classifier treats this as a shared-production-resource mutation and will block it until the user has explicitly said to proceed for that specific action.

## Domain: `www.bloommatrix.in/aira` (Next.js basePath, 2026-07-02)
- Aira is proxied under Bloom Matrix's domain via Vercel rewrite (`/aira` + `/aira/:path*` → Aira's Vercel URL) + Aira's own `next.config.mjs` `basePath: "/aira"`. Two separate Vercel projects, not merged.
- **basePath does NOT auto-prefix**: `public/` folder assets (`sw.js`, icons, favicon — must hardcode `/aira/...` in every reference, including inside `public/sw.js` itself since it's a static file Next never touches), `metadata.icons`/`metadata.manifest` string fields in `layout.tsx`, `app/manifest.ts` fields (`start_url`/`scope`/`id`/icon `src`), and any raw `<a href="/...">` — **including dynamic `href={someVar}`, not just literal strings**. It DOES auto-prefix `next/link`, `useRouter().push()`, `redirect()` (server actions/middleware — `NextResponse.redirect(nextUrl.clone())` in middleware also auto-reapplies basePath), and `next/image`.
- **Audit trap**: a literal-string grep (`grep -rn 'href="/[^/"]'`) will NOT catch `href={item.href}` (array/variable-driven nav, e.g. `operator-sidebar.tsx`'s top nav) — this exact gap caused a real prod 404 on Fleet/Schedulers/Audit Log after the migration. Full sweep needs `grep -rn '<a\b'` and manual triage, not a literal-string pattern. Also: `grep -E` does not support `(?!...)` lookahead — a pattern using it silently matches nothing rather than erroring, which reads as a false "all clear."
- Backend CORS (`backend/app/main.py`) must explicitly list the new origin(s) — it does not infer them from `FRONTEND_URL`-adjacent domains or wildcard beyond `*.vercel.app`. `https://www.bloommatrix.in` and `https://bloommatrix.in` are both now in the allowlist.

## Broadcast delivery & retry
- **Delivery truth = `messages.delivery_status`** (+ `delivery_error_code`/`_title`), set by the delivery webhook (webhook.py ~L463-517). `broadcast_recipients.send_status` only reflects **Meta API acceptance** (returns message_id), NOT delivery — it's the WRONG signal for "did the lead receive it."
- **`broadcast_recipients.send_status` delivery-failed flip is DEAD CODE** (3 reasons: CHECK constraint rejects `'delivery_failed'`; executor stores `meta_message_id` only on `messages`, not the recipient row, so `.eq` matches nothing; errors swallowed). Never trust `send_status` for delivery.
- **Per-send / per-broadcast attribution = `services/delivery_status.py` `nearest_record`/`nearest_status`** (the outbound `messages` row nearest in time, −2min/+10min). Used by all 3 sites (upload.py history+segment CSV, tags.py stats) so they never disagree. **NEVER** use max-priority-in-window (an adjacent broadcast's `sent` masks this one's `failed`) or any-failed-in-window (over-attributes).
- **`leads.whatsapp_undeliverable`** = sticky lead-level "is this number currently reachable" flag (resets on inbound + delivered/read receipt). Good for re-engagement skip; **WRONG for per-broadcast stats** (never reset per send).
- **Error codes:** `131049` = marketing cap ("healthy ecosystem engagement") — manifests async as a `failed` webhook OR a silent accepted-never-delivered; retry-worthy. `131026` = wrong number → set `whatsapp_undeliverable`, never retry. Transient set `{131049,131048,131056,130472}` does NOT set undeliverable.
- **Auto-retry (migration 104):** eligibility = "sent but no delivered/read receipt by cutoff" minus undeliverable/opted-out/replied-since/disengaged (`outbound_no_reply_count>=3`). Each attempt = a CHILD `scheduled_broadcasts` row (`retry_of`/`retry_attempt`) the 1-min scheduler sends. Per-broadcast toggle; fires at wall-clock time in tenant tz with a **≥20h guard** (cap must have reset). `services/broadcast_retry.py`.
- Both `broadcast_recipients.meta_message_id` and `leads.whatsapp_undeliverable` exist in prod but were added manually — **no migration**. Durable fix (not done): store `meta_message_id` on the recipient at send time for an exact join.

## Scoring (`services/scoring_engine.py` v2, on main)
- Composite: `arc + intent_delta + engagement_delta`, clamped 1–10. Language-aware arc (Tamil/Hindi rejection patterns). Rejection sentinel → instant score=1/segment=D on stop/not-interested/வேண்டாம். Segment lock: upgrade immediate, drop needs 2 consecutive confirmations. Engagement decay every 6h. Arc fallback on Groq failure = current arc, not hardcoded 5.
- **The segment-A/assigned gate is GONE (2026-06-01).** Scoring fires on every inbound unconditionally.
- **Per-broadcast scoring (migration 076):** `broadcast_lead_scores` table, `UNIQUE(broadcast_id, lead_id)`, seeded score=5/seg=C per send; arc window restricted to messages **after `broadcast_sent_at`** so a cold biscuit reply can't poison the ice-cream score. `compute_score(broadcast_context={broadcast_id,broadcast_sent_at,tag_id})` writes both the per-broadcast row and global `leads`. Rolls up to `lead_tag_interest` (most-recent broadcast wins).
- `lead_scorer.py` (legacy two-pass) is still called only on the AI-disabled branch — tech debt to retire (see backlog).

## Call evaluation (`call_summarizer.py` / `call_scorer.py` / `call_digest.py`)
- Two scores: `call_logs.score` (per-call, set once at outcome-mark, never changes) vs `callers.overall_score` (rolling, recomputed twice — at outcome-mark, then after AI eval ~1-2min later). Composite `_effective_score = 0.5×outcome + 0.5×AI`; no AI eval → 100% outcome (no penalty).
- **Gate before Whisper** (`_run_summarization`): skip AI entirely if outcome ∈ {no_answer, voicemail} or duration<30s. Halves token cost (~$3-5/mo total at 10 callers × 50 calls).
- `analyze_call()` = single merged LLM pass (summary + evaluation). `_GROQ_SEMAPHORE = asyncio.Semaphore(5)` guards burst at shift-end. Monthly winner needs ≥20 calls. Daily digest job fires 14:00 UTC.

## Knowledge base (pgvector RAG)
- Jina `jina-embeddings-v3` @512-dim (Matryoshka-truncated), `JINA_API_KEY`. **Why Jina:** Groq has no embeddings API; Supabase `gte-small` is English-only (app serves Tamil/Hinglish → silent degrade); Voyage had no usable free tier. Jina = free 10M tokens, true multilingual.
- RPCs (`insert_knowledge_chunk`/`match_knowledge_chunks`) take the embedding as **text** and cast `::vector(512)` inside (sidesteps supabase-py vector serialization).
- Modes via `kb_retrieval_mode` per-tenant: semantic (default) | keyword (tsvector+pg_trgm, no Jina) | hybrid (RRF). **Always falls back to full-text injection** on error/empty. `reply_source="knowledge"`.
- **Gotcha:** `create table if not exists` no-op'd against a leftover `vector(768)` table → inserts 400'd → silent full-text fallback. Always check for pre-existing tables before `if not exists`.

## Frontend performance pattern
- **Recipe:** `page.tsx` (async server component) fetches a seed via `lib/serverApi.ts serverFetchJson<T>(path, token, 2500ms)` (timeout-guarded → null on fail; MANDATORY or a cold backend white-screens SSR) → passes to a `<Route>Client.tsx` as SWR `fallbackData`. **Gate on DATA presence, not role** (seeded owners skip the spinner).
- `lib/api.ts apiFetch`: GET-only retry (network/timeout/502-503-504) + backoff + 30s GET timeout. **Mutations NEVER retry** (no double broadcasts/sends/assignments).
- Server components: `import type` for `@/lib/api` types (it pulls the browser supabase client).
- Render free tier sleeps after 15min → cold-start tail + **in-process APScheduler doesn't run**; keep-alive cron pings every 14min. One scaling caveat: externalize APScheduler before running >1 backend instance.

## Frontend styling conventions (Tailwind + `.input` utility)
- **`globals.css`'s `.input` class (padding/border-radius/focus-ring) and a Tailwind padding utility (`pl-9` etc.) on the same element are both single-class-specificity — which one wins is cascade-order-dependent, not guaranteed.** The existing convention in this codebase (e.g. `templates/page.tsx` search box) is to override `.input`'s padding via an inline `style={{ paddingLeft: ... }}` instead of a `pl-*`/`pr-*` Tailwind class, since inline style always wins regardless of stylesheet order. Follow this pattern rather than fighting the cascade with utility classes. Custom bordered controls that don't use `.input` at all (e.g. the select/dropdown wrappers on that same page) sidestep the issue entirely.
- **Brand color for interactive UI state is `primary` (violet, `#5b21b6`)**, not `emerald`/`green` — emerald is reserved for "Approved"/status-positive semantics elsewhere (template status badges, stat tiles). Active toggle/tab states in a control bar should use `text-primary`/`bg-primary`-family classes, not emerald, to stay visually consistent with what emerald already means in this app.

## Telecalling assignment (services/assignment.py)
- **State-based, not transition-triggered** (the original leak: channel webhooks force-assigned ungated, promotions never assigned). One `maybe_assign_lead()` funnel gated on `telecalling_config` (enabled+segment+channel; channel=None bypasses for call/manual/CSV) at every promotion site, PLUS a 2-min `sweep_unassigned_leads` guarantee.

Live Call Shield: `is_caller_on_call()` — a caller mid-call can't be taken over. **Auto-reassignment was REMOVED 2026-07-01** (`process_callback_reassignments` deleted) in favor of claimable-only notifications — see Callback notifications below.

## Chat escalation (ai_reply.py / chat_handovers.py)
- **Trigger-only:** A=fallback, B=AI/LLM error, C=user asked for human (always fires), D=repeated question, F=AI said team will follow up. `_TRIGGER_PRIORITY = ["C","B","A","D","F"]`. **Trigger E (score-hot) was DROPPED** — no score/segment chat escalation.
- **No auto-assign:** handovers land UNASSIGNED in a shared pool visible to admin + every telecaller (caller scope = `assigned_to == me OR needs_human_attention`). `needs_human_attention` set on escalation, cleared on resolve.
- **UI & Search (2026-07-07)**: Handovers list container size is set to `max-w-7xl` for full screen readability and has search filters targeting lead names, phone numbers, and messaging channel usernames. The settings menu/cog was removed from the bottom of `InboxRail` in conversations to simplify the screen.
- **Language mirroring is NOT reliably controllable via ANY preemptive prompt instruction, confirmed twice (2026-07-06, 2026-07-13)** — `sarvam-30b` strongly anchors to the *script/style of its own immediately preceding reply* in a multi-turn conversation, and this beats explicit instructions even when those instructions are deterministic and unambiguous, not just softly worded. Confirmed via live testing (not guessed), two separate attempts: **Attempt 1 (2026-07-06)** — reworded LANGUAGE RULE as a positive trigger: explicit verbal switch requests ("in English please") ARE followed reliably (3/3), but silent script switches (Tanglish → pure Tamil script, or Tamil script → pure English, no announcement) are NOT (0/3). **Attempt 2 (2026-07-13)** — added a deterministic per-turn script tag (`_latest_message_script_note()` in `ai_reply.py`, computed via Unicode-block counting on the customer's literal latest message, not a keyword guess) and tested it in two prompt positions (top of system prompt; immediately adjacent to the final user turn) — **still 0/6 on silent switches across both placements**, while explicit-request and no-switch cases stayed 9/9 correct. **Conclusion: this is not a wording or placement problem — the model will override an explicit current-turn instruction in favor of its own recent reply pattern, specifically and only for silent switches.** Any future fix here needs to either change what the model *sees* (e.g. shrink/filter conversation history so there's less of its own prior style to anchor to — untested as of 2026-07-13) or catch it after the fact (post-reply script-mismatch check + regen, or human handover) — do not attempt a third preemptive-instruction variant without a reason to think it differs mechanistically from the two already tried. **Rule for future work here**: never trust a prompt-engineering claim on reasoning alone — run it live 3+ times per scenario before claiming it works. See decisions/log.md 2026-07-06 and active-backlog.md for full detail and remaining options.
- **Robust Multilingual Escalation Triggers (2026-07-07)**: `_HUMAN_REQUEST_RE` and `_AI_ESCALATION_RE` use flexible regex patterns (not static lists) to handle tenses, Romanized Indian languages (Tanglish, Hinglish, Tenglish), and native Indic scripts (Tamil, Hindi, Telugu, Kannada, Malayalam). **Gotcha**: Native Indic characters do not behave reliably with standard python regex word boundaries (`\b`) due to Unicode combining marks; native script patterns must omit `\b` check to match correctly.

Dedup ids must be stable across polls AND unique per problem — incident ids fold in the incident row PK (token_invalid incidents are per-(tenant,channel) by design; keying only on tenant collapses them). - **Auth-gating shape (layout.tsx)**: `/operator/me` outcomes classify into three flags — admin / unauthorized / unreachable — and `redirect()` is only called OUTSIDE the try/catch (Next's redirect throws; a catch swallows it). 5xx/network/timeout renders `BackendUnreachable` (retry screen), never a redirect — a Render cold-start must not eject a logged-in operator.
- **Row keyboard-nav trap**: clients-page cards/rows are `role="button"` with `onKeyDown` — the handler MUST guard `if (e.target !== e.currentTarget) return;` or Space/Enter on nested checkboxes/buttons bubbles up and navigates instead.
- **Dark-mode blocker**: tailwind.config.ts colors are hardcoded HEX (not CSS vars), and `bg-x/10` opacity modifiers require migrating to `rgb(var(--x) / <alpha-value>)` triplets before any `.dark` override can work. Full decided approach in `docs/plans/operator-console-qa-and-features.md` Task 10 (deferred by user 2026-07-02).
- **`maybe_single().execute()` returns `None` on zero rows** (not a response object with `.data = None`) — code that does `if not X.data:` without first checking `if not X:` will crash with `AttributeError: 'NoneType' object has no attribute 'data'` the first time zero rows match. This has now bitten **five separate times**: `get_subscription` (2026-07-02), `approve_request`'s `existing` lookup (user-fixed 2026-07-04, commit `96fbf37`), then in the same 2026-07-04 session **three more**: `GET /api/v1/subscriptions/me`'s `sub`, `submit_request`'s `existing` (status check), and `GET /operator/clients/{id}/entitlements`'s `sub` — all in the itemized-subscriptions code, all "tenant has no `tenant_subscriptions` row yet" (the normal state for any brand-new tenant). **Symptom is misleading**: the crash response carries no CORS headers, so the browser reports it as a CORS policy block, not a 500 — don't waste time re-checking the CORS allowlist when you see this, check for an unguarded `.data` access first. `client_overview`'s `tenant`/`owner_row` lookups in `operator.py` have the identical unpatched shape as of 2026-07-02 — still no reported failure, but same landmine. Given ad-hoc grep-and-fix sweeps keep missing instances, the durable fix is a shared helper (e.g. `fetch_one(query) -> dict` returning `{}` on zero rows) that every `maybe_single()` call site routes through — not on anyone's plate yet.
- **Transient Supabase/Postgrest disconnects** (`httpx.RemoteProtocolError: Server disconnected`) hit `operator.py` routes intermittently under load — `_execute_with_retry()` (retry the `.execute()` once on a recognized transient-error string) now wraps `client_config` and `get_features_catalog`. Two other patterns for this same failure class exist elsewhere: `dependencies/auth.py` (`_verify_remote`, retry once then 503) and `chat_handovers.py`'s `handover_count` (catch and return a safe default for a non-critical poll). Extract a shared helper if a 4th call site needs it.

Don't conflate the two — PWA-only tenants still get zero automatic tracking.**

### SIM call tracking — Android "Aira Sync" APK (`android/`, 2026-07-02)
- Companion native app, NOT part of the PWA/Next.js build. Purely a background sync daemon — no CRM UI, no dialer of its own. Reads `CallLog.Calls` via `ContentObserver` (near-real-time) + a 30-min `WorkManager` periodic fallback, filters to numbers matching the caller's assigned leads (`GET /calls/sim-lead-numbers`), and POSTs matches to `POST /calls/sim-cdr` with `X-Sync-Token` auth. `callers.sync_token` (migration 122) is the per-caller secret, minted via `POST /callers/{id}/sync-token` (owner-only).
- **Fail-closed privacy filter**: if the lead-numbers fetch fails, `SyncWorker.kt` returns `Result.retry()` and uploads nothing that round. Personal calls are never even attempted for upload — the filter runs before any network call to `/sim-cdr`.
- **Foreground service permission ordering is load-bearing**: `SyncService.onCreate()` MUST call `startForeground()` unconditionally first (Android kills a service that doesn't enter foreground promptly), THEN check `READ_CALL_LOG` and `stopSelf()` if missing. Registering the `CallLog.Calls` `ContentObserver` before checking the permission throws an unhandled `SecurityException` and crashes the whole app on first launch — this was a real shipped bug, fixed 2026-07-02. `AiraSyncApplication.onCreate()`/`BootReceiver` must also gate `SyncService.start()` behind a permission check, or the service (and its crash) fires on every app relaunch/reboot before setup is complete.
- Not on Play Store — `READ_CALL_LOG` is Play-restricted to default-dialer apps; distribution is sideload-only (APK download from the site).
- Double-count risk: unreconciled with the PWA cockpit's own `sim_started` row creation (see `sim-dialer.ts`/`useCallingCockpit.ts` above) — if a telecaller dials via both paths for the same call, two rows can result. See active-backlog.md.
- **Enrichment reconciliation is order-independent (fixed 2026-07-03)**: the lookup in `_ingest_sim_call` that matches a fresh APK sync to an existing PWA-created row is gated ONLY by `call_sid IS NULL` (not by `status IN (sim_started, initiated)`) — so it doesn't matter whether the wrap-up form or the APK sync completes first, they always converge on one row. The `updates` dict the APK path writes must stay hard-facts-only (`call_sid`/`status`/`disposition`/`duration_seconds`, outcome only if the human hasn't already tagged one) — never `notes`/`tags`/`quality_rating`/`manual_started_at`/`manual_ended_at`, which stay human-owned regardless of ordering.
- **Recording upload (Phase 2) was built, then reverted 2026-07-05** — see decisions/log.md for the full writeup. Root blocker: whether a phone auto-records calls at all depends entirely on which app is set as the **default dialer**. Google's Phone app (common default even on non-Pixel phones) gates recording behind a manual per-number whitelist (Play policy, region-gated) — it does NOT blanket-auto-record. OEM native dialers (MIUI's stock Dialer, etc.) DO auto-record unrestricted, because they're privileged system apps — this is also why the known-path folder list (`/storage/emulated/0/MIUI/sound_recorder/call_rec` etc.) only ever gets populated when the OEM's own dialer is active, not Google's. Building an in-app recorder instead isn't a viable workaround: Android has restricted the `VOICE_CALL`/`VOICE_UPLINK`/`VOICE_DOWNLINK` audio sources to privileged/system apps only since roughly Android 9/10, which is exactly why standalone recorder apps work on Xiaomi/MIUI but not stock Android/Pixel. Any future revival of this feature needs a per-telecaller onboarding check (confirm default dialer + its native recorder's auto-record setting) before assuming recordings will exist to harvest — Phase 1 (call-log metadata only) does not depend on any of this and is unaffected.

## Channel settings save path (app_settings.py PATCH /api/v1/settings/)
- **Save handlers for every channel (WhatsApp/Instagram/Facebook/Telegram) MUST be DB-write-only — no outbound HTTP calls.** WhatsApp/IG/FB saves always were (upsert credentials, set `{channel}_status="configured"`, return in milliseconds). Telegram's save handler was the one exception: it called `setup_telegram_webhook()` synchronously inside the PATCH request, making a live outbound call to `api.telegram.org/bot{token}/setWebhook` before responding. On Render's free tier this occasionally hung/timed out long enough that the proxy killed the connection before any HTTP response reached the browser — the frontend's `fetch()` never got a response at all (native rejection, not an HTTP error), so it fell back to a generic "Cannot reach the server" message. **Fixed 2026-07-02** by moving `setup_telegram_webhook()` out of save entirely; save now only validates the token format (`\d+:[A-Za-z0-9_-]+` regex) and persists `telegram_status="configured"`, matching the other three channels exactly. The outbound `setWebhook` call now only happens in `POST /activate` (user-initiated "Validate & Activate" button click), where a slow/failed Telegram API call is an expected, bounded, user-visible wait — not a silent request killer.
- **Diagnostic trap**: a `net::ERR_FAILED` / "Cannot reach the server" browser error with NO HTTP status code (not 400/502/504) means the TCP connection died before any response — this is NOT a CORS rejection even if the browser's console prints a CORS-looking message (Chromium shows generic CORS text for any cross-origin connection failure since it has no response headers to inspect). Rule out CORS by checking whether *other* channels' saves succeed from the same origin/session — if WhatsApp/IG/FB save fine but Telegram doesn't, the failure is channel-specific code, not CORS config. This exact confusion cost several debugging rounds before the user pointed out the differential symptom.

## Web Push
- Web Push is permission-gated from the notification bell and stored in `push_subscriptions`. Backend delivery is best-effort via VAPID keys and must not block assignments if a subscription is stale or push config is missing.
- `GET /api/v1/push/public-key` is intentionally public (`push.public_router`); it returns only the VAPID public key. Subscription save/delete/status routes stay auth-gated. Frontend `syncPushSubscription()` must no-op when there is no Supabase session so anonymous pages do not spam 401s or redirect back to `/login`.

To add a new push event, give it a key in `_NOTIFICATION_CONFIG_DEFAULT["events"]` and the panel/whitelist; unknown types default to allowed.

## Callback notifications (services/callback_notifications.py — claimable-only)
- **1-min job `callback-notifications`** replaced the old `callback-reassignment` auto-move (2026-07-01). Two passes: (1) DUE — `scheduled_for <= now` & `due_notified_at IS NULL` → push `callback_due` to the lead's **assigned** caller; (2) CLAIMABLE — `scheduled_for <= now - threshold` & `claimable_notified_at IS NULL` → `notify_callback_claimable` to the configured audience, **with NO shift/availability check** (out-of-shift owners included). Guard columns are set on fire (once-only); `reschedule_callback` nulls both to re-arm. **There is NO auto-reassignment** — overdue callbacks are pulled manually via `POST /leads/{id}/takeover` (still CAS-guarded), which now also pushes the previous owner (`callback_taken_over`).
- **Threshold + audience are config:** `notification_config.claimable_threshold_minutes` (default 15); `claimable_audience` ∈ `telecallers_and_admin | telecallers_only | admin_only | specific` ("specific" uses `claimable_caller_ids`, owner NOT auto-added). Claimable recipients = enrolled callers (`active=True`, **ANY status** — push must reach app-installed-but-logged-out callers via their `push_subscriptions` row) + owner, minus the current owner.
- **Gotcha:** the migration-122 guard columns (`due_notified_at`/`claimable_notified_at`) MUST exist before the job runs, or the `.is_(...,"null")` filters error every tick (caught per-tenant, logged, no-op). v1 limitation: push `tag` falls back to the bare type (no `dedupe_lead_id`), so simultaneous same-type pushes can collapse on the device lock screen — the in-app bell keeps all.

### Operator Console — Itemized Subscriptions (2026-07-04, client-driven cart — supersedes the 2026-07-02 admin-assigns-one-plan model above)
- **The model changed from "admin assigns a tenant one plan" to "tenant builds their own itemized cart, admin approves it."** `tenant_subscriptions.plan_id` still exists but is now just a display-only "started from this package" pointer — **never authoritative for entitlements**. Assigning entitlements to a tenant now only happens by approving a `subscription_requests` row (`POST-adjacent` `PATCH /operator/subscription-requests/{id}`), never by a direct admin action on the tenant.

## WhatsApp templates & admin notifications (2026-07-03)
- **`notification_config.py`'s merge is hand-rolled per-key, not a generic deep merge.** `get_notification_config` explicitly special-cases `events`/`quiet_hours`/`whatsapp_notifications` by name and whitelists specific scalar keys from the stored row. A new nested config key will NOT survive automatically — it must be added to `_NOTIFICATION_CONFIG_DEFAULT`, the merge block in `get_notification_config`, AND `NotificationConfigIn`'s Pydantic schema + `update_config`'s explicit persistence dict, or it's silently dropped (Pydantic ignores unknown fields by default; the PUT handler only writes keys it explicitly lists).

No Celery in this codebase. Fire-and-forget pattern used: `asyncio.get_running_loop().create_task(...)` guarded by `try/except RuntimeError` (no-op + log if no loop), with the task held in a module-level `set()` (`task.add_done_callback(set.discard)`) — otherwise it can be garbage-collected mid-flight, a well-known asyncio gotcha.
- **For single/low-volume `send_template_message` calls, pass only `tenant_id`** (not `phone_number_id`/`access_token`) — `meta_cloud._creds()` resolves the tenant's primary WhatsApp number internally. This is the pattern `reengagement_service.py::_send_step_template` already uses. Only bulk broadcast senders (`broadcast_executor.py`, `upload.py`) need the heavier `outbound_router.get_best_number`/`increment_send_count` pair for per-number rate/quality tracking — don't reach for that pair on a low-volume alert path.
- **`message_templates` has a `UNIQUE(tenant_id, name)` constraint checked in app code before Meta is ever called** (`templates.py::create_template`, line ~91). A POST with a name that already exists locally 409s regardless of that row's `status` — including a row that failed at Meta and never got a real `meta_template_id`. Repair path is PATCH (only allowed when `status` is `REJECTED`/`PAUSED`) or DELETE+recreate, never a second POST with the same name.
- **`whatsapp_notifications.recipient_phones` must never overlap with a real/test lead's own phone number in the same tenant (learned 2026-07-06)** — the admin segment-change alert sends to every number in `recipient_phones` whenever ANY lead crosses into a `target_segments` value, with the LEAD's name filled into the template. If an admin/tester's own number is both the recipient AND a tracked lead, they'll receive alerts about *other* leads' (or their own) segment changes on the same WhatsApp thread they use for customer-side testing — reads exactly like a broken duplicate-auto-reply bug but is pure config. Also confirm `template_id` actually points at internal-facing admin copy ("Lead {{1}} just moved to {{2}}") — `aira_connect` (the default in at least one tenant) is a customer-facing "thanks for reaching out" template and produces nonsensical copy when used for this alert.
- **Meta template hard rules learned from live rejections** (Graph API `error_subcode`): `2388299` = a `{{n}}` variable can't be the first or last token of the body — trailing punctuation right after the last variable (e.g. `{{4}}.`) is NOT sufficient, Meta wants real trailing text/words. `2388293` = "words ratio" limit on variable count vs. body length — formula is undocumented; treat as a soft heuristic (roughly 6+ words per variable), not a hard rule. Positional `{{n}}` must be numbered sequentially from 1 with no gaps. All three are now validated both client-side (`frontend/app/dashboard/templates/types.ts::validateTemplateBody`/`templateBodyWarning`) and server-side (`templates.py` Pydantic validators on `CreateTemplate`/`UpdateTemplate`) — the deterministic two are hard-blocked, the ratio one is a warning only.

## Ad attribution — Meta CTWA vs Google tag (webhook.py, 2026-07-05)
- **Two independent attribution mechanisms feed the same `leads.ad_campaign_id` + `ad_campaigns` table**, both in the WhatsApp webhook's inbound loop, Meta block first then Google:
  1. **Meta CTWA/referral** — `msg.get("referral")` with `source_type=="ad"`. ONLY Meta populates this (Click-to-WhatsApp, and the parallel FB/IG DM webhooks). Google/organic messages never have it.
  2. **Google tag** — `parse_google_ref(body)` looks for a `[GADS:<slug>]` tag in the message text, injected via a `wa.me?text=` pre-fill on the Google ad. This is the ONLY way Google traffic gets attributed — Google cannot send Meta's referral object.
- **Order + guard is load-bearing**: the CTWA block sets a local `ad_attributed` bool; the Google block runs `if not ad_attributed` AND only writes when `leads.ad_campaign_id` is currently null. So Meta always wins if both are somehow present, and a repeat tagged message never re-stamps or duplicates the campaign. Don't reorder these or drop the null-check — you'll double-count or let Google overwrite a Meta attribution.
- **Tag format lives in ONE file** (`services/google_ads_attribution.py`) used by BOTH the parser (webhook) and the link generator (`/inbound-leads/google-link` endpoint + UI modal). If you change the regex, the generator's `[GADS:...]` output must change with it — the `test_build_link_round_trips_through_parser` test is the tripwire. `external_campaign_id` is namespaced `google:<slug>` to avoid colliding with Meta numeric ad ids in `get_or_create_campaign`'s external-id lookup.
- **`gclid` is captured but inert** — parsed and logged, not yet resolved against the Google Ads API. Real Google spend / cost-per-lead is NOT populated (unlike Meta where `ad_campaigns.spend_inr` can be set). The comparison-table USP shows lead *counts* per platform today, not cost, until the gclid→Ads-API reconciliation is built.
- **Attribution depends on the client using the generated link.** A bare `wa.me` number with no tag → lead stays `organic`, Google uncredited. This is why the generator is a UI button (no hand-typing) — but it's still a client-onboarding dependency, not something the platform can enforce.

## Client RBAC roles and user management (2026-07-12)
- RBAC is tenant-scoped through `tenant_roles` plus `tenant_users.role_id`. A user has exactly one role. Owners remain legacy `tenant_users.role='owner'` and implicitly receive all permission keys; non-owner users resolve their role through `resolve_permissions()`.
- `tenant_roles.permissions` stores flat Aira permission keys (`roles.manage`, `team.view`, `telecalling.dialer`, etc.), not the ERP-style nested `resource -> read/write/delete` matrix. The frontend sidebar, route access, and backend `require_permission()` must all read from this same resolved permission set.
- The Roles UI presents a read/write matrix, but it maps to flat keys. Read keys are distinct where read-only access is needed (`outbound_leads.view`, `templates.view`, `roles.view`, telecalling `*.view`, etc.); write/manage keys stay separate (`outbound_leads.manage`, `templates.manage`, `roles.manage`, `telecalling.dialer`, etc.). In the UI, selecting Write should add both read and write keys, but selecting Read must never add write.
- `roles.view` is the read-only Roles-page permission. `roles.manage` is still required for create/edit user and role mutations. Owner/master users are special legacy owners and should be shown as Master/Boss rather than ordinary assigned users.
- The default `Telecaller` role is load-bearing. `ensure_default_roles()` is idempotent and intentionally tolerates the `/rbac/roles` and `/rbac/users` parallel first-load race by reselecting after a duplicate insert. Keep that behavior; otherwise first-page loads can intermittently 500.
- Team membership is now derived from RBAC: assigning a role with slug `telecaller` or permission `telecalling.dialer` creates/activates the caller profile; removing that permission deactivates the caller profile. Do not reintroduce a separate "Add Telecaller" path in Team unless the product model changes.
- Provider-aware telecaller fields: SIM Basic tenants should expose/edit phone only; TeleCMI tenants expose/edit phone plus TeleCMI agent ID in the Roles user form and Team live-agent cards. TeleCMI password remains a backend/config concern, not a normal role assignment field.
- Password policy: admin-created users get a temporary password and `force_password_reset=true`. Admins may see only newly generated temporary passwords from create/reset actions. Admins must never be able to view a user's changed password.
- Production error trap: `PGRST205 Could not find the table public.tenant_roles in the schema cache` means the live Supabase/PostgREST schema cannot see the table, even if local code is correct. Apply/verify migration `139_repair_tenant_rbac_schema_cache.sql` against the same Supabase project used by Render; it grants Data API access and sends `notify pgrst, 'reload schema'`.
- The role create/edit form intentionally has no description field. Backend `RolePayload` accepts only `name` and `permissions`; `description` is kept nullable in the table only for backward compatibility/system rows.

## Dashboard analytics RBAC and Supabase migration ledger (2026-07-12)
