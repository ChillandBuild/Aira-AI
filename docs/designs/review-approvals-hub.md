## Problem Statement

Knowledge Auto-Sort (pending sorted uploads) and the Consistency check (contradictions between sources and the Services page) each hold something the client must approve before it changes what the AI tells customers. Nothing reaches replies until approved, so an approval nobody sees means the AI silently lacks knowledge the client believes it has. Today the two are shown inconsistently and signalled nowhere.

Verified in code this session:
- ConsistencyPanel is mounted on the Knowledge page (`frontend/app/dashboard/knowledge/page.tsx:893`) and the Services page (`frontend/app/dashboard/services/page.tsx:133`). Not on Products (catalog).
- KnowledgeReviewModal is mounted only on the Knowledge page (`knowledge/page.tsx:2001`), from a per-file Review button.
- No sidebar badge, banner or count exists for either. `frontend/components/sidebar.tsx` has count badges for Inbox (`/api/v1/chat-handovers/count`, polled every 60s) and call alerts (`/api/v1/calls/alerts/count`, polled every 60s), but none for Knowledge, Products or Services.

## Demand Evidence

Weak, and stated as such.
- Founder says they watched a client hit this ("visible on Services and Knowledge, not clear where else"). No named client, no recorded behaviour, no missed-review case was given when asked.
- Live DB, 2026-09-29 (counts only): `knowledge_reviews` holds 6 rows ever across 2 tenants (3 applied, 2 discarded, 1 pending). The one pending review was created 2026-09-24, five days ago and still unapproved. 3 tenants have a consistency report, 13 issues in total (open vs dismissed not split out).
- One five-day-old pending review is consistent with invisibility. It is one row, and it may be a test tenant. It is not proof.
- Volume is small. The hub is justified by "nothing waits unseen" as the feature grows, not by current traffic.

## Status Quo

Two separate approval surfaces on the Knowledge page (per-file Review modal, consistency panel), a second copy of the consistency panel on Services, nothing on Products or anywhere else. A client on Home, Products or Settings gets no signal that something is waiting.

Target: a tenant user with `knowledge.view` (sees the list) or `knowledge.manage` (can act). Named client: none yet (see The Assignment).

What the count counts: `knowledge_reviews` rows with `status='pending'` (the review row is the source of truth for a pending sort, not the document status) plus consistency issues that are open (not in the report's `dismissed` list). Documents in `sorting` or `failed` state do not count and are not listed in v1.
4. The count endpoint reads the stored report with `consistency.load_report` and `visible`, never `current_report`. Verified: `current_report` (consistency.py:406) calls `gather()`, which reads the business description, intake config, catalog and every indexed document's full text on each call, to compute the staleness fingerprint. Too heavy for a 60s poll, and it still makes no model call. The count therefore ignores staleness: a stale report can show a stale count until the hub re-checks. Cost per poll: one settings read, one query on the tenant's pending `knowledge_reviews` rows and one id-and-name query on the tenant's `knowledge_documents` limited to those review document ids; no `gather()`, no model call. Verified against the live DB: the only non-primary index is `(tenant_id, document_id, created_at DESC)`, whose `tenant_id` prefix serves the filter; the status filter then runs over one tenant's rows (6 rows exist in total), so no new index is needed. A tenant with no stored report counts 0 consistency issues, no error (`load_report` returns `{}`; `visible` returns no issues). Orphans cannot exist: `knowledge_reviews.document_id` is `REFERENCES knowledge_documents(id) ON DELETE CASCADE` (migration 190_knowledge_auto_sort.sql), so deleting a document deletes its review. Forged rows can: that foreign key does not check tenancy, so a review row could point at another tenant's document (knowledge_sort.py:564-568, security review 2026-09-18). The shared helper therefore fetches the tenant's pending reviews, then runs one query on `knowledge_documents` filtered by `tenant_id` and `id IN (those document ids)` (id and name, which also supplies the title; bounded by the number of pending reviews; the pending-reviews query itself has no explicit limit, which is fine below about 100 pending reviews, the same threshold as the pagination revisit), keeps only pending reviews whose `document_id` came back, and keeps one review per `document_id`, the latest by `created_at`, matching `_pending_review` (knowledge_sort.py:577). A review that could not open therefore never counts. `/approvals/count` and `/approvals` share this one helper, so the badge and the hub total cannot disagree; tests cover the shared-set equality, a forged cross-tenant row (excluded) and two pending rows for one document (counted once).

ConsistencyPanel today is mounted on Services unconditionally and its read endpoint requires `knowledge.view`, so a Services user without it already gets no usable panel; they now get no link either. Products link stays, for a concrete reason: the consistency check compares the Products catalog (`catalog_items` name and price) against the description and documents (`gather()`, consistency.py:65), so a price clash is fixed from Products. The link shows the same total N as everywhere (no per-page filtering), so the number is never different between pages.
6. Services keeps its role as source of truth but loses the embedded panel, replaced by the "N waiting in Review" link. Fixes still edit the other side via the existing `apply_fix`.
7. The per-file Review button on Knowledge stays and opens the same KnowledgeReviewModal. The modal is mounted in two places (Knowledge, hub); the panel goes from two mounts to one.

### Backend (read-only, no schema change)

- The new router lives in `backend/app/routes/approvals.py` and is mounted in `main.py` at `/api/v1/approvals` next to the consistency router (main.py:669); this is the part that must deploy before the frontend.
- `GET /api/v1/approvals/count` returns `{count, sort_count, consistency_count}` (`count` is their sum; the two existing count endpoints return only `count`, and the extra fields are additive so a caller that reads only `count` works). Tenant-scoped, guarded by `knowledge.view`. No model call, no `gather()` (Decision 4).
- `GET /api/v1/approvals` returns `{count, sort_reviews[], consistency_count}`, guarded by `knowledge.view`, every query filtered by `tenant_id`. `count = len(sort_reviews) + consistency_count`. The consistency issues themselves are not in this response: the hub renders them with ConsistencyPanel, which already fetches them from `GET /api/v1/consistency`. Duplicating them here would give two readers of the same report and an unused payload.
- `sort_reviews` is sorted oldest first by `created_at`, because the longest-waiting item is the most urgent and the card already shows its age. `consistency_count` is a number, so there is nothing to interleave. Not paginated in v1 (6 reviews ever exist); revisit past 100.
- `sort_reviews[]` item: `{ id: <knowledge_reviews.id>, document_id, title: <document name>, created_at }`. No per-item permission flag: the hub already has `canManage` and `isOwner` from `useAuthRole`, which are the same for every item.
- Panel-only context, not part of this endpoint: the panel's Fix and Dismiss address an issue by `issue_key`, the first 16 chars of sha1 of `where|document_id|normalized quote` (consistency.py:332). Unchanged.

Worked example. Tenant has one pending review for "Diwali price list.pdf" and one open issue where the file quotes "Price 4,999" but Services says 5,499. Response:

```
{ "count": 2, "consistency_count": 1, "sort_reviews": [
  { "id": "b71e...", "document_id": "d19c...", "title": "Diwali price list.pdf",
    "created_at": "2026-09-29T09:12:00Z" } ] }
```

The hub shows the review as a card and the issue inside the panel below it.
