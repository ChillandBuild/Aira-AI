## Problem Statement
When a customer leaves their number with a business, the business should send them a WhatsApp message automatically and quickly. The message must be about the exact product the customer looked at or bought. Two real-world references:
- **Ather Energy:** sign up on the website while browsing Konarc. About 5 minutes later, a WhatsApp template arrives with Konarc details and "Book Test Ride" / "Find Experience Center" buttons.
- **Supermarket / shop:** the cashier takes the number at billing, and a "thanks for purchasing" message arrives (offers come later).

Aira should offer this to any client, whether they sell through a website, an app or a physical shop.

## Premises (agreed)
1. Every first message is a Meta-approved template. The client creates and approves the templates in Aira's Templates page.
2. One message per event, with an optional delay (for example, 5 min after sign-up). Replies hand over to the existing AI chat.
3. v1 events: `interested`, `signed_up`, `purchased`.
4. Same phone + event + product within 24 h = one message. Repeats are logged, not re-sent.
5. Consent/opt-in is designed last (user's call). Until then, the snippet and quick-add form show a plain line that WhatsApp updates will follow.

## Approaches Considered
- **A) Minimal:** a generic URL plus one template per event with a `{{product}}` variable. Rejected because everyone gets the same message, which fails the exact-product requirement.
- **C) AI guesses the product from the page:** rejected for v1 because a wrong match sends the wrong product's message. Possible later as a fallback when no product field is sent.

## How other providers do it (researched 2026-10-03)
- **WATI:** a "send template message" API (phone + template name + parameters). Form → WhatsApp is done through Zapier, Pabbly or Integrately. There's no built-in product matching; the client's automation picks the template.
- **AiSensy:** "API Campaigns", one campaign per approved template. The caller posts `campaignName, destination, userName, templateParams[], media{url}`, so choosing the template per product happens on the client's side. A per-send `media.url` makes per-product header images possible.
- **Interakt:** the closest to this design. "Ongoing campaigns" are triggered by an event (sent through their Event Track API with traits like the order items), a trait update, or a time after a date. Other features:
  - advanced filters (so a campaign can target a specific product);
  - variables filled from traits, with **fallback values**;
  - **dynamic URL buttons**;
  - a delay option;
  - audience limited to `WhatsApp Opted = True`.
- **Retail POS:** Odoo-style modules auto-send a receipt template on paid orders that have a phone number. The common counter script is "Want the bill on WhatsApp?", which doubles as consent.

**What we take from this:** fallback values for every variable, dynamic URL buttons, a per-send header image, flat JSON that Zapier/Pabbly can post without code, and keeping the opt-in source on every lead now even though consent UX comes last.
**Where Aira is different:** competitors leave "which product → which template" to the client's developer or Zapier. Aira does it with no code through Catalog matching, the copy-paste snippet and the shop quick-add screen.

## Recommended Approach: B) Full Auto-Messages

### 1. One intake, three sources
All three sources post to the same intake:
- **Webhook/API:** a per-tenant secret URL, the same pattern as `marketplace_intake.py` (the token in the path is the credential). Body: `{name, phone, event, product, product_url?, extra?}`. For apps and billing software.
- **Website snippet:** a ready-made `<script>` + form the client copies from Aira and pastes into their site, with no developer needed. Fields are name, phone, and product (a dropdown filled from the client's Catalog, or a fixed value via `data-product="Konarc"` on a product page).
- **Shop quick-add:** a mobile-friendly dashboard screen for staff. Fields are name, phone, product picker (Catalog) and event (default `purchased`).

### 2. Product matching (the Konarc requirement)
- The incoming `product` is matched to a `catalog_items` row: case-insensitive name match first, then a client-defined alias list (e.g. "konarc s", "ather konarc" → Konarc).
- If nothing matches, the event goes to the **default rule** for that event, so no lead ever gets nothing. The unmatched name is shown in the send log so the client can add an alias.

### 3. Rules
- A rule is: `event + (catalog item | any) → template + delay_minutes + on/off`.
- A product-specific rule beats the "any product" rule.
- Template variables fill from the lead, the catalog item and the event's extra fields: first name, product name, price, product link (also used for dynamic URL-button suffixes). Each variable has a **fallback value** the client sets (Interakt pattern), so a missing field never blocks a send.
- If the template has an image header, it uses the catalog item's first photo, sent as a link in the template's header part (the same idea as AiSensy's per-send `media.url`).
- The setup screen suggests a **Utility** template for `purchased` (thank-you/receipt, cheaper) and Marketing for `interested`.
- Every lead stores `opt_in_source` (snippet / api / counter) now, so the later consent work has data to build on.

### 4. Sending
- Creates or merges the lead through the existing `create_inbound_lead` path (so it is assigned and shown in the inbox like any other lead).
- If delay = 0, the message is sent immediately. Otherwise a queued row is sent by the existing scheduler. In `make dev-backend` safe mode it is a dry run as usual.
- Sending goes through `meta_cloud.send_template_message`, as marketplace welcome does.
- **Send log:** who, which event/product, which rule/template, status (queued / sent / failed + reason / skipped-duplicate / no-rule).

### 5. Dashboard page: "Auto-Messages"
- Rules list, grouped by event.
- Setup for each source: copy webhook URL, copy snippet, open quick-add.
- Send log.

### Reuses
`marketplace_intake.py` (token-URL pattern), `marketplace_leads.send_welcome_template` (variable fill + approved/status checks), `inbound_lead.create_inbound_lead`, `catalog_items`, the Templates page, `meta_cloud.send_template_message`, and the existing scheduler in `main.py`.

### Not in v1
- Consent capture/records (planned last).
- Folding the IndiaMART/JustDial welcome into these rules. That code keeps working untouched.
- Multi-step sequences (thanks → offer after 7 days).
- AI product guessing.

## Open Questions
1. **Media-header templates:** decided. Use the catalog photo as the header image (see Rules). Still to confirm during build: whether the catalog storage URLs are publicly reachable by Meta.
2. **Spam on the public snippet:** anyone can post fake numbers. Plan: rate-limit per tenant + IP and drop obviously invalid numbers. An OTP is out of scope for v1.
3. **Sending window:** should delayed/purchase messages sent late at night wait until morning? Default: no quiet hours in v1.

## Success Criteria
- A test lead submitted through each source (snippet, API, quick-add) gets the template for **its** product within delay + 1 min.
- An unknown product gets the default template and shows as "unmatched" in the log.
- A duplicate submission within 24 h sends nothing new.
- Backend tests cover matching, rule priority, dedup and delay; frontend passes typecheck + lint.

## Dependencies
- The client needs approved templates (one per product they care about, plus one default per event).
- The client needs Catalog items for product matching.

## The Assignment
Pick one real client with a website and one with a shop. For each, write down 2–3 products and the exact WhatsApp message you'd want each one to get. Those become the first approved templates and the QA test cases.
